# Work-failure alerts use committed facts and the existing management route

Status: Accepted for #1041 after the first qualified private-Lark tracer passed real-platform QA and Human feedback on 2026-10-12. Source delivery and release remain separate gates.

An application-defined work-failure alert observes the Runtime-owned `sessionFailure` message after the existing Channel Store commits it. Session ownership must match the message author and execution role. Ordinary model text, tool error output and aggregate attention counts do not create alerts. The stable Bot/Channel/message identity deduplicates notification intent; the canonical failure remains in the Channel Store and native execution history remains in DSH Session Persistence.

The default-off event setting and delivery metadata belong to the existing Messaging Operational Database owner. The authenticated Bot DM Channel sidebar configures the event; no model Tool changes it or its destination. Alerts resolve the same explicit current management route used by approvals, rather than creating another destination registry or permission model. The first source candidate uses only the already-qualified Lark private destination, current Bot/App Binding and paired approver. A notice grants no Answer, Approve, Reject or rule-saving capability. Group and additional Provider qualification stay with their existing issues.

Delivery reconstructs fixed text containing failure status, execution role, Session identity and its notification reference. It never copies the canonical error detail, prompt/context, tool arguments, paths or credentials. The checked Provider must requalify the original management DM source and support reply receipt/final-send fences. Current event-setting revision, route revision, actor pairing, App identity, conversation Block, Bot readiness and Provider Registration are checked before actual dispatch. Qualification and send are bounded and run independently of the failing turn.

Known-unsent attempts can retry within one three-attempt budget, under the same current authorization. Unknown Outcome cannot be automatically or manually replayed. Restart cancels pending unstarted intents and records interrupted sending as unknown; it does not replay a failure merely because alerts are enabled again. The sidebar displays bounded recent delivery states and exposes an explicitly labelled test notice. Provider acceptance is not Human receipt or reading.

A generic output observer would confuse a model's words with failure. A second destination picker would split authorization. Retrying ambiguous sends could duplicate operational alerts. Referencing the committed failure and reusing the management owner avoids those alternatives while adding database Generation 83 for settings and notification-attempt metadata. Back up before upgrading; rollback needs a compatible writer or the pre-upgrade backup. Host/VPS-down monitoring is outside this slice.
