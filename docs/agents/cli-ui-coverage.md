## Maintained inventory

[`scripts/cli-ui-inventory.json`](../../scripts/cli-ui-inventory.json) records reviewed source surfaces with an owning scope and exactly one of:

- Existing CLI commands. These are command mappings, not claims of live/runtime verification or Tob access.
- A specific open delivery issue for the gap.
- A reasoned **nonconfigurable** exemption: media transport, rendering, draft recovery or tutorial/read receipts. Configurable preferences are never exempted merely because they live in a Client service.

The existing [`cli-parity-baseline.json`](../../scripts/cli-parity-baseline.json) remains the bridge/Host-route/Bot-tool baseline. Its #1690 gaps and justified running-Agent/UI-only exceptions are preserved. The supplemental inventory does not duplicate or waive that check.

`pnpm lint` runs both through `scripts/check-cli-parity.mjs`. The supplemental parser reads TypeScript/JSX syntax rather than searching comments or example strings. It discovers:

- Registered HTTP route objects, including imported path constants, shorthand `path`, computed expressions, prefix handlers and helper calls with an HTTP method. Finite `for…of` route families include their iterable in the identity, so adding a new action requires review.
- Client `setItem`/`removeItem` calls, including optional chaining, computed storage keys and storage injected into a service.
- Shared `SettingsRow` controls and scoped `field` controls (including Browser target/driver controls), even when their change handler calls a native Client service rather than a bridge.
- Native setting field declarations ending in `_FIELD`, including Computer settings declared outside the Client directory. Client persistence detection also covers sibling Browser/Computer Client modules.

New surfaces fail lint without a mapping; removed surfaces fail until their inventory entry is reviewed. Mapped command names must still exist in CLI sources. An exemption requires an explicit `configurable: false` declaration as well as a reason. A group records individual discovered surfaces; it is not a filename wildcard that silently accepts new settings.

This is a structural regression guard, not a whole-program proof. A new persistence API, custom control primitive, native service adapter or route factory must extend extraction and focused tests in the same PR. Dynamic route functions retain their source expression for review; the checker does not execute them or claim every runtime expansion is understood. Browser-origin state and native settings must be checked on the target Client in addition to the Host.

The existing `botharness-client.autoAcceptGroupInvites` defaults to `true`. The main journey therefore joins invited Bots immediately after Tob management approval, with `respondedBy=profile-policy`; it does not add an invitation approval step or a new UI toggle. Existing opt-out behavior remains a compatibility branch.

Creation keys bind normalized inputs and Bot incarnations. Channel fingerprints bind metadata/membership, the current invitation policy and effective member wake policies, including inherited defaults, without invalidation by message traffic or unread changes. Stale review or unavailable targets refuse; receipts never revive a deleted group or changed Bot identity. Group content cannot grant Tob management authority, and Tob does not join managed groups.

The settings/removal slice adds no schema or UI. All scoped edits require `--expected-channel`, recheck accepted Human DM authority and current Human group access around approval/execution, and reject stale snapshots or replaced targets. Human CLI equivalents keep optional fingerprints for compatibility. These edits do not use operation keys: after uncertainty, read current state and prepare a fresh reviewed proposal if still needed. Existing create/invite receipt semantics stay unchanged.

Pending cancellation/decision commands also require `--expected-channel`, bind the exact record and target incarnation, and recheck current Human membership and pending status before execution. They introduce no schema, Tool or receipt. Human join-decision calls without a fingerprint retain same-decision idempotent readback; scoped Tob accepts only pending records. After uncertain outcomes, inspect canonical status/membership before a new proposal, without blind replay or a fallback from cancellation to member removal.

Personal preference commands read a separate `stateFingerprint` and submit it as `--expected-state`, rather than using a group-management fingerprint. It binds the target identity and four preferences; edits to another Channel neither invalidate it nor get overwritten. They act for the stable Human in the current Host Profile, recheck Channel access and reviewed state, and read back the existing RosterStore/ChannelStore owners. Scoped writes require the fingerprint; Human online writes may opt in. This is Host-persisted per-Human/per-Channel preference, not a device-local layout setting or display-name-based identity. It adds no permission to replace whole rosters or manage other settings.

## Updating the inventory

For each new UI setting or action, identify its durable owner and scope first. Reuse its existing CLI command when equivalent; otherwise record the smallest delivery issue. A combined group is acceptable only while all recorded members share the same mapping or gap. Split a group when one operation becomes covered, remove stale mappings, and preserve precise nonconfigurable exceptions.

For Client settings, acceptance must prove which Client changes, a reload/restart readback, and that another Client or Channel is unaffected. For Host mutations, test the direct CLI independently of the model, then the real Tob conversation and canonical readback. Approval, revoked/stale context, unsupported operations and failed readback remain coded outcomes, never fallback access.

## #2099 Profile backup repair boundaries

The source command contract binds scoped recovery review to its Model Plan revision and recovery fingerprint at the owning commit, with current accepted-source authority rechecked after asynchronous validation. Owner refusal codes survive the scoped broker. Human preview/download writes a private sibling stage and atomically publishes only verified complete bytes without replacing an existing destination. Scoped export receipts use the already-known preview ID for read-only completed-result reconciliation, including after broker restart.

Restore preserves content but revokes imported paired-device credentials/Host identity, push destinations, remembered secret-MCP approval and protected Tob role before publishing the new stopped Profile. Existing grant/rule/messaging/schedule/execution suspension remains. Target-local device pairing, secret authorization and a new protected Tob identity must be established under current Human authority. These source contracts and authored regressions do not qualify Web, real Tob, restart, process-kill or macOS behavior; the original source selector failure remains unpassed evidence.
