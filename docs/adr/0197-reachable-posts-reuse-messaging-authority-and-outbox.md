# Reachable posts reuse Messaging authority and Outbox

[ADR-0142](0142-a-bound-app-admits-its-direct-messages-and-mentions.md) authorizes proactive posting wherever the platform permits the Bot's owning app to speak. #1115 implements that decision through the application-defined Messaging Provider Service Definition; it creates no additional DSH Service or persistence authority.

The Provider optionally lists current reachable groups and performs a source-free checked post with an authenticated account fingerprint, exact conversation ID, synchronous final caller fence and native receipt. Discovery is permission evidence at one instant; native membership/speaking permission is checked again at dispatch. Lark, Discord and Slack implement this optional capability. Other Providers keep their saved-target route until they implement it.

The application-defined Host owns Binding, conversation blocks, per-app quota and Outbox. A first reachable post creates one existing implicit conversation entry after current ownership and block checks. It does not synthesize a Source Event, Inbox Admission, local Human DM or Channel placement. Current mute/held policy does not prohibit an explicitly authorized proactive post; a durable block does. Existing checked saved-target posts retain their own route and digest rather than silently switching to discovery.

Schema Generation 89 adds the Binding post limit, default 60 per rolling hour; null disables it. A separate quota revision rejects stale limit edits without changing the Binding revision used by reception, replies and typing. Quota changes do not restart the receiver; proactive final fences still read the current limit. Outbox attempt-start facts are the quota source. A started unknown outcome consumes a slot and retains its request identity. Identical requests return the canonical result and never resend after restart. Block, unbind, archive and Provider replacement fence unstarted effects; acceptance after a native effect remains an acceptance fact.

The Client retains bounded recovery drafts in tab-local storage scoped to the existing Host/Profile/Human identity, Bot, Binding and fingerprint. These are request IDs and presentation state, not sending authority or a second Outbox. Closing the picker or reloading the Client does not allocate a fresh ID for an unresolved post. The existing Typert/API Gateway exposes an exact, read-only Host request lookup; it correlates the owning Bot, Binding, conversation and payload against canonical Outbox facts, without consulting a live Provider or creating an effect. Reopening and pending-result polling use that lookup. An explicit lost-response retry uses the original ID and reads or completes that same canonical Host request; unknown outcomes remain unsendable. A received receipt remains a fact after later unbind or permission loss. Only a definite Host result permits a subsequent explicit post with a new ID. Corrupt or unavailable recovery storage refuses new effects, and late responses cannot replace a newer request or downgrade a received receipt. No recovery draft sends automatically.

Main-line Generations 84–88 retain their Assignment archive, Inbox resolution/snooze, Assignment access-scope and remembered secret-MCP migrations unchanged. Earlier task-only #1115 Generations 84, 87 and 88 used different migration histories and must remain isolated; they are not supported main-line upgrade sources. The prior native evidence remains attached to those exact candidates, while main-line Generation 88 → 89 upgrade coverage preserves existing QQ/WeChat Binding and reception authority.

The existing Typert/API Gateway connects the Host operation to the app's Client picker and native Agent Tool Consumers. Registry/Registration and Fiber disposal remain the process-lifecycle boundary; operational database records remain the durable application authority. The main-line connected-app Tool selection also controls `bridge_reachable_groups`: it appears with the other Bridge Tools only while this Bot has IM. [Provider .20 qualification](../evidence/issue-1115/provider20-qualification.md), the #1111 Provider-release prerequisite and sibling QQ permission work remain distinct delivery gates. Historical evidence from the closed experimental branch is not qualification of this rebuilt revision.
