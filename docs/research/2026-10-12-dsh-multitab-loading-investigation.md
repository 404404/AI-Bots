# DSH multi-tab loading investigation — 2026-10-12

## Scope and evidence standard

**Local follow-up, October 13, 2026:** the disposable RC2 upgrade passed install/typecheck/build and 53 focused tests, but reproduced the same-origin two-page loading failure. A repeated browser/request-observer loop measured six simultaneous HTTP/1.1 long-lived responses and recovery within 4–8 ms after the peer left, without changing credentials or restarting the Host between cycles. Independent authenticated requests remained responsive. The original upstream-only findings below retain their source/observation boundaries; the new evidence and limitations are in [the local RC2 qualification report](../qa/issue-1459-acceptance/rc2-multitab-follow-up.md). RC2 alone does not clear #1459's multi-tab acceptance gate.

Upstream-only investigation of browser loading freezes, HTTP/SSE connection pressure, browser authentication, HMR, and historical remedies. Primary authority is **deepseek-ai/deepseek-harness** source, commits, and first-party Agent Notes. The final appendix incorporates explicitly supplied parent-investigation observations; those were **not independently reproduced here**. No running Host, browser, credentials, production configuration, commit, or push was touched. Upstream code was read from an isolated research checkout; this report is the only delivery file.

**Confirmed-source** means inspected code or an upstream historical statement, not a newly reproduced runtime result. **Parent-observed** means supplied by the parent investigator. **Hypothesis** means a causal explanation still requiring local measurements. ## 2. Executive findings

1. **Confirmed-source: upstream has documented this exact class of multi-tab connection-slot problem.** Its August 4 WebSocket note says the old browser GUI kept two SSE downlinks (`events.mux`, `events.host`) open per page; on HTTP/1.1, the approximately six-connection per-origin budget could queue tabs, plugin resources, and ordinary RPCs. This is upstream's historical explanation, **not a measurement of this BotHarness incident**. [Historical note](https://github.com/deepseek-ai/deepseek-harness/blob/d743267388641bc76f17c45ce8b4c231aed1d32c/.agents/notes/archived/architecture/2026-08-04-websocket-downlink-carrier.md).
2. **Confirmed-source: rc.1 already contains the remedy and its successor.** August's first fix replaced the two native downlinks with WebSockets; subsequent Gateway work multiplexed native Remote streams onto **one physical WebSocket**. It is incorrect to diagnose rc.1 as still using the old pair of native SSE streams. [Original fix](https://github.com/deepseek-ai/deepseek-harness/commit/8b4ddfe60c751f4596e497b739ef6b4979104bc1), [rc.1 mux client](https://github.com/deepseek-ai/deepseek-harness/blob/4878cdabd87d4041bdaff61d04c966883b9fd07a/packages/api/gateway/src/client/stream-client.ts#L46-L59).
3. **Confirmed-source: native HMR remains a separate SSE channel**, despite the native Remote WebSocket. Its browser Plugin constructs an EventSource and closes it on Fiber effect disposal; its Host endpoint holds `text/event-stream` responses. That leaves a plausible connection-pressure mechanism for application-defined SSE streams, but does not prove their actual count or the freeze's cause. [rc.1 browser HMR](https://github.com/deepseek-ai/deepseek-harness/blob/4878cdabd87d4041bdaff61d04c966883b9fd07a/packages/client/hmr/src/client/index.ts#L24-L46), [rc.1 Host HMR](https://github.com/deepseek-ai/deepseek-harness/blob/4878cdabd87d4041bdaff61d04c966883b9fd07a/packages/client/hmr/src/index.ts#L158-L207).
4. **Confirmed-source: rc.1 already has launch-token exchange, signed authority-bound cookies, and synchronous authentication.** These are not fixes available only on current master. Newer native HTTPS cookie changes must be distinguished from this existing mechanism. [rc.1 auth](https://github.com/deepseek-ai/deepseek-harness/blob/4878cdabd87d4041bdaff61d04c966883b9fd07a/packages/client/connection/src/browser-auth.ts#L180-L310).
5. **Confirmed-source: recovery is bounded per attempt, not a cure for arbitrary application loading waits.** rc.1 has the September 5 stalled-handshake deadline and continuous capped retries. These do not free unrelated EventSource connections, refresh invalid credentials, or establish that application-defined loading work belongs to the native generation lifecycle. [Continuous-recovery note](https://github.com/deepseek-ai/deepseek-harness/blob/d743267388641bc76f17c45ce8b4c231aed1d32c/.agents/notes/archived/bug-fix/2026-09-05-continuous-client-recovery.md).

## 3. Native transport: historical fix versus rc.1/current

### Historical predecessor and remedy

The August 4 implementation changed the physical **Host-to-browser downlinks** to two independent WebSockets, retaining HTTP POST for uplinks. Its design explicitly rejected a network SSE fallback because that would retain the connection-limit problem. The historical note explains why HTTP/2 could not be assumed: the built-in server used plaintext Node HTTP/1.1, not a guaranteed proxy arrangement. [Original implementation](https://github.com/deepseek-ai/deepseek-harness/commit/8b4ddfe60c751f4596e497b739ef6b4979104bc1), [note](https://github.com/deepseek-ai/deepseek-harness/blob/d743267388641bc76f17c45ce8b4c231aed1d32c/.agents/notes/archived/architecture/2026-08-04-websocket-downlink-carrier.md).

**Do not copy that historical two-WebSocket topology into rc.1 conclusions.** The August 22 Gateway unification and removal of legacy Host event carriers superseded it. rc.1 defines `/api/remote.mux`; `RemoteStreamMuxClient` shares one physical socket across independently cancellable logical Remote streams and creates that socket using `new WebSocket(remoteStreamUrl())`. [Gateway unification](https://github.com/deepseek-ai/deepseek-harness/commit/3d6d595d794ba715c60ff850f044cc02e6c53d40), [legacy-carrier removal](https://github.com/deepseek-ai/deepseek-harness/commit/dcddaa1a6e4b386c49fdbe3a01414ad5bc0c01d5), [pinned protocol](https://github.com/deepseek-ai/deepseek-harness/blob/4878cdabd87d4041bdaff61d04c966883b9fd07a/packages/api/gateway/src/stream-protocol.ts#L1-L12), [pinned client](https://github.com/deepseek-ai/deepseek-harness/blob/4878cdabd87d4041bdaff61d04c966883b9fd07a/packages/api/gateway/src/client/stream-client.ts#L226-L245).

**Confirmed comparison:** `git diff rc.1..master` is empty for `packages/api/gateway/src/client/stream-client.ts`, `packages/api/gateway/src/stream-server.ts`, `packages/client/connection/src/client/connection.ts`, `packages/client/connection/src/recovery-config.ts`, and the inspected HMR Host/client/events source files. This is a file-specific statement, not package-wide equivalence: Gateway admission/startup handling, Connection trust/auth, packaging, and other files have changed. [Revision comparison](https://github.com/deepseek-ai/deepseek-harness/compare/4878cdabd87d4041bdaff61d04c966883b9fd07a...d743267388641bc76f17c45ce8b4c231aed1d32c).

rc.1's listener imports `createServer` from `node:http`. This is source evidence for its direct listener, **not evidence that every deployed request bypasses a proxy or uses HTTP/1.1**. [Pinned webserver](https://github.com/deepseek-ai/deepseek-harness/blob/4878cdabd87d4041bdaff61d04c966883b9fd07a/packages/host/webserver/src/index.ts#L1-L12).

### HMR is a different transport

`client-hmr` serves graph/rebuilt notifications through `/plugins/events`; its browser uses document-relative `EVENTS_ROUTE`. The Host writes an initial comment and graph, retains a response set, removes closed responses, and destroys remaining responses on disposal. It is not carried by `/api/remote.mux`. The source describes this as the Web composition's live-graph transport, not solely a development rebuild channel. Whether a particular page mounts it still requires composition/runtime evidence. [Pinned events constants](https://github.com/deepseek-ai/deepseek-harness/blob/4878cdabd87d4041bdaff61d04c966883b9fd07a/packages/client/hmr/src/events.ts), [Host lifecycle](https://github.com/deepseek-ai/deepseek-harness/blob/4878cdabd87d4041bdaff61d04c966883b9fd07a/packages/client/hmr/src/index.ts#L158-L207).

**Boundary:** native Connection owns authentication/admission; API Gateway owns Typert Remote multiplexing; the HMR Plugin owns its separate graph/rebuild stream. An application-defined EventSource does not become a native Remote stream simply because it targets the same Host. The inspected HMR route itself has no `connection.admit()` call; do not extend the `/api` authentication contract to every plugin route without checking that route and its enclosing listener. [Current Gateway admission](https://github.com/deepseek-ai/deepseek-harness/blob/d743267388641bc76f17c45ce8b4c231aed1d32c/packages/api/gateway/src/index.ts#L240-L263), [HMR handler](https://github.com/deepseek-ai/deepseek-harness/blob/4878cdabd87d4041bdaff61d04c966883b9fd07a/packages/client/hmr/src/index.ts#L180-L207).

## 4. Browser authentication and token predecessors

### Confirmed rc.1 contract

- The query parameter is `token`; the process-owner token is retained in a WeakMap across Connection reloads. The persistent credential record supplies a signing secret loaded during activation. This is not a token stored in browser localStorage or an API bearer contract. [Token owner](https://github.com/deepseek-ai/deepseek-harness/blob/4878cdabd87d4041bdaff61d04c966883b9fd07a/packages/client/connection/src/browser-auth.ts#L12-L57), [secret initialization](https://github.com/deepseek-ai/deepseek-harness/blob/4878cdabd87d4041bdaff61d04c966883b9fd07a/packages/client/connection/src/browser-auth.ts#L161-L215).
- A valid single token on the root GET exchanges for a signed cookie and **303** to `./`, with `no-store` and `no-referrer`. A stale token URL with an already valid cookie also redirects cleanly. Otherwise index authorization responds **401**. Exchange is not visibly single-use: the inspected valid-token branch does not consume or invalidate the process token. [Exchange and rejection](https://github.com/deepseek-ai/deepseek-harness/blob/4878cdabd87d4041bdaff61d04c966883b9fd07a/packages/client/connection/src/browser-auth.ts#L238-L279).
- rc.1 hashes the normalized Host authority into the cookie name and includes the same authority in its signed payload. Validation checks signature, authority, issued/expiry times, and configured maximum lifetime; default `cookieMaxAgeDays` is **30**. Cookie attributes are `Path=/`, `HttpOnly`, `SameSite=Strict`, `Max-Age`, and `Expires`; the rc.1 serializer does not add `Secure`. [Cookie encoding](https://github.com/deepseek-ai/deepseek-harness/blob/4878cdabd87d4041bdaff61d04c966883b9fd07a/packages/client/connection/src/browser-auth.ts#L69-L129), [validation](https://github.com/deepseek-ai/deepseek-harness/blob/4878cdabd87d4041bdaff61d04c966883b9fd07a/packages/client/connection/src/browser-auth.ts#L282-L310), [default](https://github.com/deepseek-ai/deepseek-harness/blob/4878cdabd87d4041bdaff61d04c966883b9fd07a/packages/client/connection/src/index.ts#L103-L135).
- Authentication is synchronous after activation, avoiding credential-provider reads on each request. The upstream auth note says an unexpired cookie survives an ordinary restart on the same authority with the same durable signing secret; deleting the record requires subsequent activation to revoke existing sessions. The process launch token changes on process restart. [Auth note and its verification limits](https://github.com/deepseek-ai/deepseek-harness/blob/d743267388641bc76f17c45ce8b4c231aed1d32c/.agents/notes/implemented/architecture/2026-08-24-browser-token-authentication.md), [synchronous-auth fix](https://github.com/deepseek-ai/deepseek-harness/commit/9c964848cd54d6e9a7d5f01f1745936673cd1910).

**Hypothesis, not observed here:** pages under different hostname/port authorities, expired cookies, a changed signing-secret context, or rejected trust/Origin conditions could produce repeated authorization failures. That predicts returned 401/403 or failed upgrades, not by itself a queued request with no response. Continuous recovery explicitly does not refresh invalid credentials. A completed 401 and a transport-pending request must therefore remain different diagnoses. [Recovery consequences](https://github.com/deepseek-ai/deepseek-harness/blob/d743267388641bc76f17c45ce8b4c231aed1d32c/.agents/notes/archived/bug-fix/2026-09-05-continuous-client-recovery.md).

### Current master difference

The native HTTPS change `ac080346f037f7d4d4054ca311cd3a5081b847a6` is **not an ancestor of rc.1**. Current auth takes the receiving listener's `secure` state, adds `Secure` for native TLS, and scopes HTTPS cookie audiences to the protocol-inclusive origin while retaining HTTP's authority-only spelling. Do not project these newer semantics onto rc.1 or infer them from a public URL/forwarded header. [HTTPS implementation](https://github.com/deepseek-ai/deepseek-harness/commit/ac080346f037f7d4d4054ca311cd3a5081b847a6), [current audience/serializer](https://github.com/deepseek-ai/deepseek-harness/blob/d743267388641bc76f17c45ce8b4c231aed1d32c/packages/client/connection/src/browser-auth.ts#L69-L134).
