# Bot mode is a dockable layout that plugins extend with Dock panels

DeepSeekBot can already do far more than DSH's native shell shows, and Humans will add their own extensions: a goal tracker, a to-do list, or another store DSH does not have, like the Bot Inbox did. Such an extension needs a place on screen. Most Humans will not want every extension, so these extensions should stay plugins rather than built-ins, and BotHarness should make writing one easy. Today the desktop Bot mode panel has three fixed regions: the DSH-native App Sidebar on the left, the Channel body in the center, and the Channel sidebar on the right with icon tabs ([ADR-0183](0183-channel-sidebar-is-tabbed-and-configuration-lives-in-channel-settings.md)). Only the Channel sidebar width can change. A plugin can add a Channel sidebar entry, but it cannot add a region, and the Human cannot rearrange anything. We decided: **on desktop, Bot mode becomes one dockable layout that the Human can rearrange freely, but that stays as plain as an IM client such as Slack: each panel stands alone, with no tabs. The qualified wide shell contains a full-height control rail, an independent Channel list, the Channel body and Dock panels inside one workspace; unqualified shells keep the Bot mode sidebar fallback. Other DSH plugins add their own Dock panels through a BotHarness Service, and each Human arranges a browser-local layout.**

## Decision

### Scope

- **Desktop Bot mode only.** The Bot mode layout exists only while the Client is in Bot mode at 961 px or wider. Outside Bot mode, DSH's native shell is unchanged. Below 961 px the Client falls back to today's responsive layout, where the Channel sidebar is an overlay of collapsible entries. The saved layout is kept and returns when the window widens again. Phones keep their current layout.

### Channel selection preserves layout lifetime

The Channel selection is not a React identity for the workspace or Dock. Switching by shortcut, roster, profile navigation, or the welcome view updates the active scope without recreating unrelated Panels. Transient conversation state and refs reset per selection generation; callbacks retained by a departed generation cannot write into the new one, even after returning to the same Channel. Composer drafts remain in the existing per-Channel draft owner. Only affected content and its scope-bound resources restart.

### Execution stays on DSH

- **The Bot mode layout is presentation only.** It changes where things appear on screen. It does not change how work runs. A PersonaBot is still an abstraction on top of DSH Sessions: the Orchestrator Session, Assignment Sessions and every Bot tool call run through DSH's Session execution and its plugin ecosystem. The Human talks to a Bot rather than to a raw Session, but each turn still runs in a DSH Session. A Dock panel, including one from a third-party plugin, reaches the Host only through DSH Services and the existing Host↔Client seam, and never through a second execution path.

### A scoped workspace replaces the sidebar allocation (#2017)

- **One workspace in qualified wide shells.** The control rail, global Channel list (`bh:channels`), unique closable Messages panel and other Dock panels share the same Dock layout. The rail cannot close, float or join a tab. It occupies a full-height root column and can move before any other root column, including a column containing vertically stacked panels. The rail contains the DSB exit control, panel switches and settings. The Channel list uses the existing Roster and active-Channel owner; it does not copy selection or Channel data.
- **Local compatibility adapter, qualified against DSH 0.2.0-rc.2.** The native sidebar Slot shadow remains the fallback. While the wide workspace mounts, `workspace-shell.ts` checks AppFrame's grid and direct Slot containers, scopes markers to that frame, hides only its sidebar container, sidebar handle and leading seat, and lets `main` span the first two grid tracks. It does not write the native layout Store, width preference or collapse state. Exit, narrow mode and unmount remove its markers. An unknown shell or Windows caption layout keeps the existing sidebar implementation. #1794 remains the route to a supported upstream API, not a delivery blocker.
- **One temporary command owner.** Native and Web shortcut resolvers call the public `layout.toggleSidebar()` method. The adapter temporarily routes that command to the Channel list panel, covering customized bindings too. It restores the exact original property descriptor on release, provided no later owner replaced it. Failure to claim the method leaves the native layout intact. This override is a version-qualified compatibility shim, not a new DSH extension API; review and rerun shell and shortcut tests on DSH upgrades.
- **macOS chrome is local to the top-left corner.** The 88px leading footprint follows rc.2's traffic lights and measured native placement. Only top-row groups intersecting it reserve inline header space; a rail in that corner places its first control below the lights. Other panels use the top of the window. A small native drag region occupies the reserved corner and the Channel topbar exposes native window dragging. Fullscreen removes the reservation. Windows remains on the fallback until its caption controls are qualified.
- **One browser-local record.** `botharness.bot-mode-layout` version 2 contains Dockview geometry, remembered closed-panel neighbors, rail switch order, group-member split ratio/open state and a continuous 0–16px spacing value (default 4px). Version 1 migrates without dropping panel subtrees or parked positions. Closed Channel and Messages panels remain closed on refresh and reopens from the rail or sidebar shortcut. Invalid nested rail placement is removed and reinserted as a full-height column. The main workspace stays usable before a Channel is selected.
- **Spacing separates surfaces.** Small round panels use an 85% base / 15% surface token mix, close to the original base-color workspace background; the macOS traffic-light corner uses that same base background; header/body spacing is `min(4, gap / 2)`. The setting applies immediately and persists in the same record. Inner content surfaces remain owned by their panel (#2006 is separate).

- **Messages owns the group-member split.** Group Members is opened from the Messages header and shown on its right, with a resizable 20–60% width persisted in the same record. It is absent from the global rail and from direct messages. Existing member management actions and authority stay unchanged.
- **Reorder switches and customize shortcuts.** Rail switches support drag ordering and Alt+Up/Down. DSH's native Shortcuts Service owns configurable bindings and conflict checks, surfaced in its keyboard settings. Defaults use Primary+Alt+Shift with 1–9/0/B/E; Linux Web has no default because rc.2 rejects those web bindings. Commands pass outside the active workspace or while a modal is open.
- **Preserve live panel content.** Dockview owns React Portals with `defaultRenderer="always"`. Root-rail rearrangement uses `fromJSON(..., { reuseExistingPanels: true })`; panel movement reuses the existing instances. Geometry retains Dockview grid dimensions and relative sizes with proportional layout enabled. No extra content cache or duplicate layout store is introduced. The companion suppresses the click following a drag rather than navigating to its DM.

### Layout engine

- **dockview.** The layout uses [dockview](https://dockview.dev) (React, MIT, no runtime dependencies). It provides splits, drag-to-dock and a serializable layout; its floating groups and pop-out windows are turned off. It is themed only through the dsh-ui token alias table, so the shell stays visually native.
- **One panel is one panel: no tabs.** A panel never shares its space with another panel as a tab. Each dockview group holds exactly one panel, and its tab strip is replaced by a plain panel header with the title, which is also the drag handle. Dropping a panel onto another panel's center (which would tab them) is disabled; dropping on an edge splits the space. Panels sit next to each other, as in Slack.
- **No floating, no pop-out windows.** Every panel is docked. A panel cannot float above the layout or pop out into a separate browser window.

### Dock panels

- **Built-in Dock panels.** The built-in panels are the Channel body, the **Activity Center**, and one panel for each Channel sidebar entry: Sessions, Bot Inbox, Memory files, Memory evolution, Schedules, Computer, Browser, and any plugin entry. Entries that ADR-0183 put together under one tab, such as Sessions with Bot Inbox, or Memory files with Memory evolution, are now separate panels.
- **Activity Center is a `global` Dock panel** (`id: 'activity-center'`, amended for [#1829](https://github.com/BotHarness/DeepSeekBot/issues/1829)). It shows the same Overview and Human Inbox as the full Activity Center page, so the Human can keep it open next to the Channel body. Its tabs are local to the panel, and opening a Channel from it leaves the panel open. The full page remains the destination on fallback narrow layouts and phones; the qualified workspace can open it as a panel before selecting a Channel.
- **Exactly one Channel body.** At most one Channel body exists. In the qualified workspace it is the closable Messages panel (`bh:channel-body`), reopened from the rail or a customizable shortcut; legacy fallback keeps the body open. Selecting a Channel changes what it shows. Several Channel bodies, whether as tabs or side by side, are rejected, because they would make the interaction and the screen too complex.
- **The Channel list selects the active Channel.** Selecting a Channel in the Channel list Roster makes it the active Channel. The Roster highlights it, the Channel body renders it, and every `channel`-scoped Dock panel shows it.
- **Each panel declares its scope.** A `channel` panel follows the active Channel. A `global` panel, such as a to-do list, does not follow it. A `channel` panel with nothing to show for the active Channel, such as a DM-only entry while a group is active, shows an empty state rather than disappearing, so the layout does not jump.

### The Dock panel registry

- **A Cordis Service.** The BotHarness Client provides a `dockPanels` Service (`ctx.provide`). A plugin is a Consumer that `inject`s it and calls `register(panel)`, and gets back a disposable. A registration carries a stable `id`, `title`, `icon`, `scope` (`global` or `channel`), a `defaultPosition` hint (a zone `left | center | right | bottom`, optionally relative to another panel id), an optional `order`, and a React `component`. Registration, removal and ordering follow the Registry rules of [ADR-0053](0053-channel-sidebar-is-the-scoped-right-sidebar.md). Ids are owned by their plugin, and registering a duplicate id throws.
- **`channelSidebar` stays as a compatibility Consumer.** `channelSidebar.register(entry)` registers a `channel`-scoped Dock panel. `registerTab(tab)` turns into a default-layout hint that places its entries next to each other, split rather than tabbed. Entries with `surface: 'settings'` remain Channel settings sections. The narrow overlay still renders entries the way it does today. Existing callers, such as the Computer and Browser plugins, keep working unchanged.

### Data belongs to the plugin's own capability seam

- **A Dock panel is only a UI Consumer.** A plugin that keeps data, such as goals or to-dos, follows DSH's Capability seam (`Consumer → Service Definition → Provider`). It defines its own Service and a Host Provider that persists the data. The Dock panel and the plugin's Bot tools are both Consumers of that Service. BotHarness adds no generic panel store, and the Bot mode layout never holds plugin data.
- **CLI parity applies to the plugin's Host surface, not to the layout.** The layout is browser-local presentation, with no bridge method, Host route or Bot tool, so it has no CLI command. A plugin's own bridge methods, routes and Bot tools follow [CLI parity (AX)](../../AGENTS.md#cli-parity-ax) as usual.

### The Human arranges the layout

- **One layout per browser, plus Reset.** The layout lives in browser localStorage under a new key, as a versioned dockview serialization. When restoring, panels that are not registered right now (a plugin was removed) are skipped, but their last position is remembered and reused when they register again. Saving named layouts is deferred. On first load, the existing `botharness.channel-sidebar` width seeds the right column. Because panels are never tabbed, every open panel is visible at once, so the default layout opens only a few: the control rail and Channel list on the left, the Channel body in the center and Sessions above Bot Inbox on its right, which matches today's default Sessions tab. Every other panel (Memory files, Memory evolution, Schedules, Computer, Browser, plugin panels) starts closed and is opened from the rail (or the Panels menu in the fallback). When it opens, it splits into the right column unless its registration asks for another position.
- **Pinned panel controls in the rail and fallback sidebar** (amended for [#1829](https://github.com/BotHarness/DeepSeekBot/issues/1829)). The workspace rail shows a vertical icon stack; the fallback Bot mode sidebar below its brand row shows a row of small cards, one per registered Dock panel (including Messages in the workspace; excluding the body in fallback), like a browser's pinned tiles. A card shows its panel's icon, is highlighted while that panel is open, and toggles it through the `dockPanels` Service (`toggle`, `openPanels`, and `available` for whether a layout is mounted); it never touches dock internals. The Activity Center card replaces the old Activity Center row and keeps its unread count and action dot. While no layout is mounted, on the fallback surface, the Activity Center card opens the full Activity Center page and the other cards are disabled. On the collapsed rail the cards become a vertical icon stack. The workspace rail replaces the Panels menu; fallback layouts retain that menu.
- **A Panels menu replaces + Views on desktop.** The fallback Channel body header has a **Panels** button, like VS Code's View menu, because the Channel body is the one panel that is always open. It lists every registered Dock panel except the Channel body, each with a checkbox. A panel that is closed and then reopened returns to its last position, or to its default position if it has none. The menu ends with **Reset layout**; the workspace moves Reset into Bot Settings → Workspace layout. Workspace panel headers omit close buttons; the Workspace Control Rail owns visibility. Fallback panels other than the Channel body retain their header close button. The Channel list moves Search, list options and Create into its panel header without a second Messages heading. DM context menus expose View profile and anchor directly to viewport pointer coordinates.

### Making plugins easy to write

- **Example plugin, guide and skill.** The same change train ships a minimal example plugin. It contains a to-do Service with a Host Provider, a Bot tool with its CLI command, and a `global` to-do Dock panel. It also ships a bilingual authoring guide and a skill, so that a Bot running in DSH's creative Profile, which can author plugins, can build a panel for itself by following them.

## Delivery

These are tracer-bullet slices. Each one ends in a state the Human can run and judge.

1. **Docked Channel** ([#1789](https://github.com/BotHarness/DeepSeekBot/issues/1789)). Desktop Bot mode renders dockview inside `main`, containing the Channel body and every Channel sidebar entry as Dock panels, through the `channelSidebar` compatibility Consumer. Panels can be dragged and docked by splitting, and are never floated or tabbed. The layout persists browser-locally and the narrow fallback still works.
2. **Public registry** ([#1791](https://github.com/BotHarness/DeepSeekBot/issues/1791)). Add the `dockPanels` Service with `global` and `channel` scopes, the Panels button and Reset layout. Seed the layout from the old preferences and retire + Views on desktop.
3. **Example plugin and guide** ([#1792](https://github.com/BotHarness/DeepSeekBot/issues/1792)). The to-do example plugin with its Service, Provider, Bot tool, CLI command and Dock panel, plus the authoring guide and skill.
4. **Bot mode sidebar** ([#1790](https://github.com/BotHarness/DeepSeekBot/issues/1790)). Shadow `sidebar` at `-1` in desktop Bot mode and draw the Bot mode sidebar with the Roster and an Exit Bot mode control. It does not depend on the dock and can run in parallel with slice 1.
5. **Upstream** ([#1794](https://github.com/BotHarness/DeepSeekBot/issues/1794)). File the DSH layout API request with the evidence from #1790 and track it.
6. **Pinned panel cards** ([#1829](https://github.com/BotHarness/DeepSeekBot/issues/1829)). Replace the Activity Center row in the Bot mode sidebar with pinned panel cards, and make Activity Center a `global` Dock panel.

7. **Workspace rail and Channel list** ([#2017](https://github.com/BotHarness/DeepSeekBot/issues/2017)). Release native allocation locally on qualified rc.2 shells; validate movement, continuous spacing, persistence and native restoration before extending the panel matrix.

## Considered Options

- **motion-panels.** Rejected as the engine. It animates split panes, with fold, collapse and snap animations on resize. It has no tabs, no docking between groups, no floating groups and no layout serialization. It is also pre-1.0 with one maintainer.
- **Make the App Sidebar a Dock panel that keeps the native sub-slots.** Chosen first, then rejected after checking DSH `0.2.0-rc.2`: a `sidebar` shadow does not free the column's width and cannot render the native sub-slots. The native sub-slot preservation still needs an upstream API; #2017 locally releases allocation without preserving those hidden contributions.
- **Keep the native App Sidebar in Bot mode.** The lowest-risk option, since every plugin's left-column contribution keeps working. Rejected because the Human wants Bot mode to have its own sidebar.
- **Collapse the native column and dock our sidebar inside `main`.** Rejected. On the web a 56 px rail remains, and collapsing flips the Human's own sidebar preference.
- **Fixed zones only (left, center, right, bottom).** Rejected in favour of full docking, which is the VS Code experience the Human asked for.
- **Tabbed panel groups and several Channel bodies (VS Code style).** Rejected. Tabs inside a panel and several open Channels make the interaction and the screen too complex. An IM client such as Slack shows that one panel per region is easy to understand.
- **Declarative panels generated by a Bot without code.** Deferred. Code plugins come first. A Bot in the creative Profile can already write a code plugin, so it gets the same result once authoring is easy.
- **A generic BotHarness panel store.** Rejected. Storage belongs to each plugin's own Service and Provider, the way DSH composes capabilities.
- **Host-synced layout and named layouts.** Deferred. Host sync would add a bridge surface and a CLI command for what is presentation. One browser-local layout plus Reset matches how Channel sidebar preferences work today.
- **Only the Panels menu, with no sidebar entry for panels.** Rejected by the Human for #1829: panels keep growing, and cards show at a glance which are open and toggle them in one click.
- **Floating panels inside the window.** Rejected for now by the Human. Docked panels alone keep the layout simple; floating can return later if a panel needs it.
- **Pop-out browser windows.** Rejected. Rendering React across windows and keeping DSH Context alive in them is costly, for little benefit.

## Consequences

- On desktop, this supersedes ADR-0183's tab strip, its top and bottom split, and the + Views menu. ADR-0183 continues to govern Channel settings and the narrow overlay. ADR-0053's entry Registry rules carry over to Dock panels.
- Bot mode owns its left column and the layout of its `main` area, which moves DeepSeekBot closer to a standalone product that runs on DSH. The dsh-ui rule "shadow only `sidebar.workspaces` and `main key=conversation`" gains one exception: desktop Bot mode shadows the whole `sidebar` slot at `-1`. DSH tokens, primitives and the inset contract still apply in the Bot mode sidebar and inside every Dock panel. Because a DSH change to the `sidebar` slot can now break Bot mode, the pinned-release end-to-end tests cover workspace entry, native shortcut routing, macOS chrome, responsive fallback and exit restoration. The local shell/command adapter must be requalified on every DSH upgrade.
- dockview adds to the Client bundle, and its CSS must be fully mapped to DSH tokens.
- `verify-deepseekbot`'s feature map, `CONTEXT.md` and the living architecture are updated when each slice lands.
