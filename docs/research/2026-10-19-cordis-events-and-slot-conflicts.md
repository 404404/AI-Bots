# Cordis Events and native Slot conflicts

Date: 2026-10-19. Source-only research for panel design Q9 (keep notifications simple; no replay) and Q10 (follow DSH conflict handling). No Host was launched, no tests executed, and no implementation decision is made here.

## Native facts: Event dispatch and replay

1. **`emit` is synchronous dispatch, with no listener-failure isolation.** It invokes callbacks through `map(cb => cb(...args))`, without `try/catch` and without awaiting or attaching rejection handlers. A synchronous throw propagates and prevents later callbacks from running. A returned rejected Promise is not handled by this dispatcher. These are consequences of the exact 4.0.5 implementation, not assumptions based on an older version. [Cordis `emit`](https://github.com/deepseek-ai/deepseek-harness/blob/687f282e8625c6b8d11ff58211a90524be2e4317/vendor/cordis/src/events.ts#L188-L196)
2. **`parallel` starts ordinary callbacks through async wrappers, waits with `Promise.allSettled`, then throws `AggregateError` containing every rejection reason.** Thus one listener's synchronous throw or rejected Promise does not stop other ordinary listeners from being invoked; it does not make the dispatch successful. A caller must handle the returned rejection if notifications must not fail its operation. Dispatch/filter/internal-hook failures occur before this listener-settlement protection. [Cordis `dispatch` and `parallel`](https://github.com/deepseek-ai/deepseek-harness/blob/687f282e8625c6b8d11ff58211a90524be2e4317/vendor/cordis/src/events.ts#L159-L187)
3. **Ordinary Events have no replay contract.** The service stores current callback registrations, dispatches the current listener set, and registers `on` through a Fiber effect. There is no history store, cursor or catch-up loop in this mechanism. New listeners receive subsequent dispatches; disposal removes their registrations. Special lifecycle hooks are extensible and should not be confused with replay for business Events. [Cordis registration and disposal](https://github.com/deepseek-ai/deepseek-harness/blob/687f282e8625c6b8d11ff58211a90524be2e4317/vendor/cordis/src/events.ts#L254-L302)

The audit's open question about Activity's plain `emit` is therefore resolved at source level: **4.0.5 does not itself isolate failing Activity consumers.** This research has not reproduced a failure in BotHarness.

## Native facts: Slot selection, conflicts and lifecycle

| Case                     | Pinned native behavior                                                                                                                                                           |
| ------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `single`                 | The Slot is one cell. Registrations at different priorities coexist; the lowest numerical priority wins.                                                                         |
| `keyed`                  | Each `key` is a separate cell. The owner dispatches `entryKey`; that cell's lowest-priority surviving entry wins.                                                                |
| `list`                   | Each `id` is a separate cell with the same priority shadowing. Fresh ids are additive; winning cells are displayed by list order.                                                |
| Same cell, same priority | Registration throws. Omitted priority means `0`; a second default registration is a conflict. There is no last-install-wins rule.                                                |
| `chain`                  | Entries are tried by ascending priority; ties preserve registration order. The first non-null selector result wins. This is a different selection mechanism from cell shadowing. |

Sources: [native cardinality documentation](https://github.com/deepseek-ai/deepseek-harness/blob/687f282e8625c6b8d11ff58211a90524be2e4317/docs/subsystems/slots.md#L58-L75), [registration guards](https://github.com/deepseek-ai/deepseek-harness/blob/687f282e8625c6b8d11ff58211a90524be2e4317/packages/client/ui-slots/src/index.ts#L1207-L1251), [sort and winner projection](https://github.com/deepseek-ai/deepseek-harness/blob/687f282e8625c6b8d11ff58211a90524be2e4317/packages/client/ui-slots/src/index.ts#L1281-L1371).

**A contribution is not a declaration.** Declaring an already declared child Slot throws even when parent contributions use different priorities. Disposal removes the contribution and recursively collapses its declared child Slots and their contributions. Consumers use `ctx.slots.inject(key, callback)` to follow a declaration's lifetime and re-register when the owner returns. Thus replacing a parent that owns child declarations needs deliberate ownership/lifetime design; priority alone does not grant duplicate declaration ownership. [Declaration and lifecycle](https://github.com/deepseek-ai/deepseek-harness/blob/687f282e8625c6b8d11ff58211a90524be2e4317/docs/subsystems/slots.md#L15-L25), [declaration conflict guard](https://github.com/deepseek-ai/deepseek-harness/blob/687f282e8625c6b8d11ff58211a90524be2e4317/packages/client/ui-slots/src/index.ts#L1245-L1251)

## Native facts: crash fallback is different from HMR rollback

**There is native render-crash fallback for shadowing Slots.** The renderer catches a component/injection crash, reports it through the Slot supervision channel and retires that registration from winner selection for `single`, `keyed` and `list`. The next surviving registration in the same cell can render. The crashed registration remains in the ledger until its owner disposes it; merely crashing does not free its priority for another registration. If all registered candidates have crashed, the outlet shows an error marker, not its natural-empty fallback. `chain` crashes do not abdicate. Assembly failures such as missing required providers are deliberately rethrown. [Renderer boundaries](https://github.com/deepseek-ai/deepseek-harness/blob/687f282e8625c6b8d11ff58211a90524be2e4317/packages/client/ui-renderer/src/client/scoped-slots.tsx#L395-L420), [abdication implementation](https://github.com/deepseek-ai/deepseek-harness/blob/687f282e8625c6b8d11ff58211a90524be2e4317/packages/client/ui-slots/src/index.ts#L1529-L1552), [outlet handling](https://github.com/deepseek-ai/deepseek-harness/blob/687f282e8625c6b8d11ff58211a90524be2e4317/packages/client/ui-renderer/src/client/scoped-slots.tsx#L1122-L1195)

**HMR does not restore a torn-down bundle.** Download failure leaves the running Plugin active. Once teardown has occurred, import/activation failure leaves a page-local synchronization error. Settings → Plugins → Plugin list can retry the latest graph even at the same revision; a later rebuild also retries it. Successful unrelated Plugins stay active. The graph stream sends current full composition on a new connection; this is graph resynchronization, not business-event replay. [HMR lifecycle and failure policy](https://github.com/deepseek-ai/deepseek-harness/blob/687f282e8625c6b8d11ff58211a90524be2e4317/packages/client/hmr/README.md#L60-L74)

The distinction matters: a still-registered lower-ranked Slot contribution can survive removal/crash of an override, but native HMR does not recreate an old implementation it already removed. Nor do these sources guarantee that a replacement of the whole shell cannot make the normal Settings retry route inaccessible.

## Applicable recommendations — application-defined, not upstream guarantees

- **Q9:** Honor the simple live-notification contract. Do not add a generic replay log, delivery cursor, catch-up queue or exactly-once promise. A newly mounted/reconnected stateful Panel can query its owning Service for current state, then follow live notifications; missed intermediate notifications are not recovered. Transient visual reactions may simply start from their default state. A current-state read is not event replay.
- **Producer failure handling:** “No replay” does not settle failure isolation. For public post-change notifications, document a bounded error-reporting policy so an extension cannot interrupt unrelated listeners or make an already-committed operation appear failed. `parallel` plus caught/reportable aggregate failure is a native option when awaiting all listeners is acceptable. If nonblocking isolation is required, that is an explicit producer policy rather than a property of `emit`.
- **Q10:** Reuse native Slots and their exact precedence/conflict rules where Panels become Slot contributions. For a required role, a first-party lower-precedence registration can be the ordinary surviving candidate if product composition keeps it registered. Avoid inventing a last-install-wins rule or a second conflict resolver. Document native error diagnostics and retry, plus any consciously accepted limitation when replacing shell entry points.
- The current application-defined Dock Panel Registry rejects duplicate ids. Native Slot priority semantics do not automatically apply to it. Adopting them requires an actual seam change or explicit adaptation; documentation alone cannot claim that behavior already exists.

The first-party default, its priority, declaration ownership, and whether a separate recovery entrance is required remain product composition choices. Native fallback already covers a narrower, useful case; it should neither be omitted from the design nor described as universal rollback.
