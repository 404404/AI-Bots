# DeepSeekBot 产品版本规范

[English](version-policy.md) · [决策](../adr/0216-dsb-product-versions-identify-immutable-package-sets.md)
· [实施跟踪总任务](https://github.com/BotHarness/DeepSeekBot/issues/1979)

**这是已确认的规范，不是全部校验已经实现。** 当前交付状态以任务为准。
文档、构建成功、合并和里程碑都不授予发布权限；本规范补充[Release Ledger 规则](changelog.md)，不建立第二份更新日志权威。

**当前流程缺口：**既有发布器仍将预发布版本指向 `next`，不是 `beta`。在 #1982 的渠道与资格校验交付、迁移得到明确批准前，不用它向测试用户分发 Beta。[旧 npm 指南](../npm-prerelease.md)记录既有操作机制，但包含历史包范围／版本示例；其中排除 Browser／Computer 的说明相对于 `scripts/product-artifacts.mjs` 已过时。任何另行授权的发布都须核对实际冻结的 Release Plan 与产物，不能只依赖这些示例。

## 身份与归属

| 身份                          | 规则                                                                                                                               |
| ----------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| Product Release Version       | 电脑端 DSB、`deepseekbot`、`@botharness/core`、`@botharness/ui`、`@botharness/browser`、`@botharness/computer` 共用准确的 SemVer。 |
| 标签与日志                    | `v<version>` 和双语发布标题对应同一产品版本；准备候选不能伪装公共标签／Release 已经存在。                                          |
| 当前运行产品                  | Host 拥有已加载代码的身份，Web 与认证 CLI 消费同一结果，不能从 npm 移动标签推断。                                                  |
| 已安装／待生效更新            | 单独显示待激活版本；新 Host 实际启动后才能成为当前运行版本。                                                                       |
| Development Build Identity    | 明确未发布的源码／分支／dirty 身份；显示开发构建，而不是把 `0.0.0` 当作面向用户的软件版本。                                        |
| DSH／IM Provider／工具／Skill | 保持独立版本，记录准确已验证依赖及来源，不强制加入产品同号发布。                                                                   |
| 手机                          | 独立原生版本、构建计数器和源码／产物身份；电脑补丁不要求重建未改变的手机包。                                                       |
| 产物／组合                    | 保留完整包清单、校验和及源码；手机与电脑资格绑定准确产物，不靠数字相同证明兼容。                                                   |

发布元数据缺失／损坏、产品组件不一致必须明确返回 unknown／错误，并在必要时提供 coded refusal，不能悄悄退化为开发模式。
源码内部可以保留 `0.0.0` 占位，但它不是发布权威。公开来源记录不能包含本机路径、token 或私人数据。

## 版本选择与渠道

维护者在既有准备流程只选择一次版本；冻结的 Release Plan 绑定版本、源码和完整产物，各包清单由此生成。
后续命令校验预期版本／源码／计划摘要，不能重新选择候选。

- Patch：兼容修复；Minor：兼容新功能；Major：破坏已承诺支持的用户行为、CLI、配置或协议。
  依赖升级按对 DSB 的实际影响判断，不是每个 PR／迁移都要升大版本或立即发布。
- 正式版 `X.Y.Z` 使用 `latest`；测试版 `X.Y.Z-beta.N` 使用 `beta`，同一目标版本线每个变化的候选递增 `N`。
  文中数字只是示例，不代表已经预留的版本。
- Nightly／CI 使用唯一源码／构建／产物身份，仅内部验证，不自动移动用户渠道。
  保留历史 Alpha／RC 日志及现有预览测试记录，本规范不新增公开 Alpha／RC 渠道。
- `next` 弃用。单独授权迁移前核对真实 registry 和旧客户端行为；最多保留为已验证正式版的旧入口，不再投递新 Beta／Nightly。
  暂无已知用户不代表零客户端，不能据此直接删除；新客户端使用 `latest`／`beta`。
- 加入渠道与发现候选不是兼容证明或发布批准；保留手机／电脑独立加入、低频更新和额度门槛。

## 候选生命周期

1. **准备**：指定一次版本并协调分配，防止同一身份出现竞争计划。复用既有打包与清单，不新增平行打包器。
   dirty 实验只能明确标为内部、未验证，不能通过发布资格。
2. **冻结**：交付 QA 时保留准确包集合与 Release Plan。源码、依赖或打包内容变化必须换版本；SHA／SemVer 不能单独证明产物字节。
3. **验收**：在独立安装的受支持 DSH 与全新隔离 Profile 中安装准确产物，核对实际加载路径及 UI／CLI 身份。
   monorepo CLI 可能优先加载源码 link，而非待测包；遵循[产物验证](../product-im-installation.md)。
4. **批准**：证据及 Human 批准绑定准确计划／产物。源码测试、原生／已安装产物验证及 Human QA 分开；
   源码构建不能代替更新发现、升级或新候选提醒的发布验收。
5. **发布**：取得单独授权，先确认依赖包及 registry integrity，再推进产品入口。核验整个集合，而不只是顶层包。
6. **回读**：确认 registry／标签及真实受支持安装／升级行为，再按既有门槛更新正式安装身份及公告。
   裸 registry 解析与 DSH 预览／实际安装不一致仍归 [#1456](https://github.com/BotHarness/DeepSeekBot/issues/1456)，本地 tarball 安装通过不代表它已修复。

`2.0.0-beta.3 → 2.0.0` 即使源码相同，也是新产物身份：清单及内部准确依赖版本会改变。
必须准备、验证并批准正式产物；将 `latest` 指向 Beta 包不叫转正式。未改变的手机产物无需因此重新发布。

## 失败与恢复

版本分配／发布使用一个协调通道。npm 不提供多包事务，失败时部分依赖版本可能已经可见。
停止推进，记录哪些准确版本及 integrity 已确认，保留不确定结果；不宣布全量成功、不推进公共安装指针，
不删包假装回滚，也不偷偷重建。检查后只恢复同一批准计划／字节，已发布且匹配的包可以复用；
同名同版本 integrity 不同必须拒绝。若原已验证产物不可恢复，应分配新候选并重新验收。

界面应区分 `当前运行 2.0.0` 与 `已安装 2.0.1 · 重启后生效`。
由新 Host 真正就绪确认运行身份，而不是乐观安装响应或变更的磁盘清单；不得自动重启忙碌任务或承诺普遍可立即降级。

## 强制门槛与交付

- 准备／发布：版本、内部准确依赖、源码及 clean 状态、完整清单／来源、校验和与预期计划一致；标签／日志在真实发布阶段核验。
- 运行：区分源码、发布产物和异常身份，区分运行与待生效版本；认证 Host／CLI 与实际 Web 一致。
- 发布：验证 stable／Beta／内部／旧渠道路由、竞争分配、依赖顺序、部分失败、不确定超时及同字节重试。
- 本地 registry dry run 不是公共 npm 验收；商店上传不是测试者可安装。规范不启用调度、移动线上标签、购买构建或发布生产版。
