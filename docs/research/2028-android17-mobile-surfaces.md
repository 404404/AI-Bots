# Android 17 and Material app surfaces — visual reference (2026-10-17)

Research for #2028. This note informs the Android shell work; product choices below are recommendations, not a new platform requirement or architecture authority.

## Scope and source boundary

Android 17 is a released platform: Google's release announcement is dated June 16, 2026. Its adaptive guidance uses a navigation bar on mobile and a navigation rail on larger windows. That announcement does not establish a new universal glass treatment for app navigation. [Android 17 release](https://android-developers.googleblog.com/2026/06/Android-17.html)

Material 3 Expressive is the relevant app-component reference. Android's documentation distinguishes this design system from the operating system's visual style. Pixel notification shade, volume controls, wallpaper settings, system taskbar and app navigation are different surfaces. A system screenshot alone cannot establish the geometry or behavior of an app navigation bar. [Material 3 in Compose](https://developer.android.com/develop/ui/compose/designsystems/material3)

Image search was used for discovery, then results were traced to Google's own pages or the official Material repository. Third-party leak collages, concept renders and articles calling the design “Liquid Glass” or “Luminous” were excluded as normative evidence. The user-supplied three-phone collage has no established primary provenance in this investigation; its soft tonal separation is useful visual direction, but its pixels are not a component specification.

## Component findings

### Bottom navigation

The Expressive implementation reduces bar height from 80 to **64 dp**, item top/bottom padding to **6 dp**, and active-indicator width to **56 dp**. At widths of at least 600 dp, it supports icon and label side by side. The container's role is `colorSurfaceContainer`; selection uses a tonal indicator rather than a large uniform color wash. Labels are not made bold just because they are selected. The guide describes three to five destinations. [Pinned navigation-bar guide](https://github.com/material-components/material-components-android/blob/66b0eeb53afeb6025ffbbd37734b08e5bce197ed/docs/components/BottomNavigation.md)

**Product adaptation:** retain the two meaningful destinations already in the app; do not invent a third destination to imitate the example. Use a 64 dp content band, clear icon/label/selected-pill hierarchy and a container visibly different from the page. The requested floating capsule, horizontal margin and gap above the system gesture region are an explicit DeepSeekBot customization; they are not the default full-width component pictured above. Reserve the capsule's occupied height in scroll content, while keeping system gesture insets separate.

### Environment picker / left panel

The official Material guide deprecates the navigation drawer in the Expressive update and points to the expanded navigation rail. Its legacy modal form uses a scrim and sits above, rather than resizing, compact-screen content. [Pinned drawer guide](https://github.com/material-components/material-components-android/blob/66b0eeb53afeb6025ffbbd37734b08e5bce197ed/docs/components/NavigationDrawer.md)

The Expressive rail has collapsed and expanded configurations; expansion adds labels and resembles the former drawer. The component guide's Expressive collapsed form is 96 dp wide, with 64 dp minimum items and 4 dp spacing. These are rail measurements, not an instruction to make a phone's environment picker 96 dp wide. [Pinned rail guide](https://github.com/material-components/material-components-android/blob/66b0eeb53afeb6025ffbbd37734b08e5bce197ed/docs/components/NavigationRail.md)

The newer Compose implementation also has a modal wide rail. Its expanded-width tokens are **220 dp minimum / 360 dp maximum**, with a **16 dp** `CornerLarge` modal outline; the non-modal expanded token has no rounded outline. Modal fill uses `SurfaceContainer`. These source tokens are more precise than measuring a screenshot. [Expanded-rail tokens](https://github.com/androidx/androidx/blob/0736ae559f4e20de18f993d3b2c138a82836caf4/compose/material3/material3/src/commonMain/kotlin/androidx/compose/material3/tokens/NavigationRailExpandedTokens.kt), [shape tokens](https://github.com/androidx/androidx/blob/0736ae559f4e20de18f993d3b2c138a82836caf4/compose/material3/material3/src/commonMain/kotlin/androidx/compose/material3/tokens/ShapeTokens.kt)

`ModalWideNavigationRail` can enter from offscreen when `hideOnCollapse=true`. In its modal dialog, a full-screen `Box` draws the scrim first and panel content above it; the underlying app's layout remains fixed. Its scrim uses an effects animation separately from the spatial panel transition. The inspected rail image above is non-modal, so it does not demonstrate this scrim or modal outline; these facts come from source. [Pinned modal-rail implementation](https://github.com/androidx/androidx/blob/0736ae559f4e20de18f993d3b2c138a82836caf4/compose/material3/material3/src/commonMain/kotlin/androidx/compose/material3/WideNavigationRail.kt#L530)

**Product adaptation:** our Host selector switches connection context rather than top-level destinations. Keep its compact-screen modal interaction, but borrow the expanded rail's calmer tonal container, icon/label alignment and rounded selected row. This is a product-specific picker, not a claim to implement the newest standard navigation drawer. Keep the background inert, expose modal accessibility and preserve Android Back. Use a smaller title with a clear text hierarchy; the header should not dominate the host rows. A persistent rail is a separate large-window decision.

### Profile and settings sheets

The official bottom-sheet guide differentiates modal sheets by their scrim, supports vertical dragging and outside-tap dismissal, and documents `behavior_draggableOnNestedScroll`. Its surface is `colorSurfaceContainerLow`, with extra-large upper corners and maximum width 640 dp in the View implementation. These values are reference geometry, not React Native APIs. [Pinned bottom-sheet guide](https://github.com/material-components/material-components-android/blob/66b0eeb53afeb6025ffbbd37734b08e5bce197ed/docs/components/BottomSheet.md)

Compose's current tokens independently specify a **32 × 4 dp** handle, `OnSurfaceVariant` handle color, `SurfaceContainerLow` fill and `CornerExtraLargeTop` shape. [Pinned Compose sheet tokens](https://github.com/androidx/androidx/blob/0736ae559f4e20de18f993d3b2c138a82836caf4/compose/material3/material3/src/commonMain/kotlin/androidx/compose/material3/tokens/SheetBottomTokens.kt)

`CornerExtraLargeTop` resolves to **28 dp upper corners and 0 dp lower corners**. It is different from `CornerExtraLargeIncreased`, which is 32 dp. Consequently a 16 dp modal-rail corner is not the sheet corner token. [Pinned shape definitions](https://github.com/androidx/androidx/blob/0736ae559f4e20de18f993d3b2c138a82836caf4/compose/material3/material3/src/commonMain/kotlin/androidx/compose/material3/tokens/ShapeTokens.kt#L27)

Its nested-scroll connection consumes upward motion before the child to expand the sheet. Downward movement is consumed after the child, using the child's unconsumed delta. Thus a scrolled child gets the downward gesture first; the sheet follows when the child reaches its boundary. This is direct source evidence for the requested “content reaches top before sheet closes” behavior. [Pinned nested-scroll connection](https://github.com/androidx/androidx/blob/0736ae559f4e20de18f993d3b2c138a82836caf4/compose/material3/material3/src/commonMain/kotlin/androidx/compose/material3/SheetDefaults.kt#L631)

**Product adaptation:** use the same handle, surface, scroll handoff and Back/dismiss behavior for profile and settings. Keep the handle stationary above the scrolling content. Open the shell immediately; data loading belongs inside the shell. Skeletons are a loading-state product decision, not a reason to delay navigation. The sheet should not resize repeatedly as asynchronous sections arrive.

## Motion and rendering implications

Material's motion interface separates **spatial** specs for shape/bounds from **effects** specs for color/alpha. Both standard and expressive schemes are available. The source explicitly directs color/alpha animation away from spatial specs. [Pinned MotionScheme](https://github.com/androidx/androidx/blob/0736ae559f4e20de18f993d3b2c138a82836caf4/compose/material3/material3/src/commonMain/kotlin/androidx/compose/material3/MotionScheme.kt)

The current Compose sheet uses `defaultSpatialSpec` for showing and drag settling, and `fastEffectsSpec` for hiding. A blanket bouncy spring on every property is therefore not a faithful transfer of the official implementation. [Pinned sheet motion](https://github.com/androidx/androidx/blob/0736ae559f4e20de18f993d3b2c138a82836caf4/compose/material3/material3/src/commonMain/kotlin/androidx/compose/material3/BottomSheet.kt#L135)

**Product adaptation:** animate panel translation on the UI thread with an interruptible spring, carry release velocity where the gesture library supports it, and use a non-overshooting opacity fade for the scrim. Respect reduced motion. Keep data fetch, cache reconciliation and expensive list mounting out of the first visible animation frame. Tune actual RN spring parameters against captured motion rather than copying numeric Compose stiffness into a different solver.

The inspected app-component images use tonal fills, not mandatory live backdrop blur. A static gradient at a content/chrome boundary can supply the requested edge fade. In chat its bottom edge must follow the composer's actual keyboard-sticky coordinate space; an unrelated gradient inside the resized list viewport can leave the hard boundary the user reported. This is an application of the visual references and current layout, not an Android 17 rule.

## Review and validation targets

- Capture the same content before and after: navigation container separation, selected state, narrower Host title, search-row create action, settings gear and consistent sheet handle.
- Record tap to first visible surface change separately from data completion; simulate slow requests so a fast local Host cannot hide the loading interaction.
- Verify downward scrolling of long settings/profile content before dismissal, direct handle drag, outside tap, Back, safe areas and large font behavior.
- Evaluate streaming and gesture frame deadlines on the actual device refresh rate. A 120 Hz target has an approximately 8.3 ms frame budget; average FPS alone can hide jank. Release/profile measurements and app frame timing are needed before claiming 120 FPS. [Android rendering guidance](https://developer.android.com/topic/performance/vitals/render)

## Limits

This investigation inspected official published imagery and source; it did not run an Android 17 emulator or claim that the current Android 16 QA phone shows Android 17 system UI. The pinned AndroidX `androidx-main` snapshot is evidence for current component behavior, not the dependency shipped in this Expo app. React Native implementation and native runtime evidence must be checked separately.
