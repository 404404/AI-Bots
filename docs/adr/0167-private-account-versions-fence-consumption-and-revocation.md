# Private account versions fence consumption and revocation

The application-defined `PrivateInputs` owner maintains one current grant per PersonaBot creation identity and account. Original values remain exclusively in native Credentials Service. A separate native grant record stores only the account scope, opaque revision and active grant UUID, or a null tombstone for local revocation. The account key hashes the scope; it is not a credential value. Version-three immutable grants retain the canonical Channel request and configured-resolution proof from ADR-0166 and additionally require the exact current account binding at consumption. Neither remembered broad execution approval nor a configured historical card can bypass this check.

The Owner's existing Web Chat card exposes replacement and local revocation. Replacement opens a blank multi-field private card and never reads old values through Client APIs. An Owner-created replacement references the original card without inventing a native Session ID or restoring an Agent waiter. A subsequent real `ask_secret` obtains the current references when all declared required fields are configured. The declaration remains generic; the fixed trusted HTTP CLI consumes its own supported fields. No secret-consuming MCP, Schedule or IM adapter is added.

Each account has a Host-local serialized start/mutation queue. Replacement captures the current revision and can activate only if it still matches and the request remains valid. Native account activation precedes publication of the canonical configured Channel resolution. Consumers require both proofs; an activation failure publishes only an empty-reference expiry, and a later Channel failure leaves an unusable account head rather than reviving the old version. A fresh private request can repair that account. Native Credentials `modifyRecord` checks the expected revision inside its atomic write. A failed reply after commit is accepted only when canonical readback matches the newly generated revision and grant exactly. Owner mutations await startup recovery, which removes uncommitted or inactive version-three values and preserves account tombstones.

Consumption verifies the live Agent, PersonaBot birth, account, complete references, immutable grant and canonical Channel proof, then checks the current binding immediately before starting the trusted consumer. The account queue releases after registering that use, rather than holding it for the remote request. Revocation writes the tombstone and synchronously aborts all currently registered uses inside the same queue, preventing a later fresh setup from being accidentally stopped. Replacement also attempts to stop prior-version uses. Consumers receive a scoped AbortSignal; selected value copies are cleared after their callback settles.

Stop reporting is bounded to one second. An aborted callback that rejects is stopped; one that succeeds is already completed; a callback still unsettled is uncertain. The report cannot prove remote side effects were undone. A bounded record of the most recently observed completed account use supports the no-active-use completed report. Channel audit text explicitly describes local revocation and never claims third-party token revocation. An audit failure cannot undo committed revocation. HTTP 401/403 exposes only status and a static Web Chat replacement/remote-authorization repair action; response bodies, headers and error details remain discarded.

Version-one and version-two grants remain consumable only before their account has a binding. The first replacement or revocation makes all other old UUIDs unavailable. This is a one-way security migration despite no Profile schema generation change: an older binary ignores tombstones and may revive old grants. Back up the Profile before upgrading; repair forward or restore the full pre-upgrade backup. Never downgrade a Profile containing retained grants to an unfenced binary.

Rejected alternatives include mutating values behind a stable reference, deriving authority from UI state, treating remembered approval as credential authorization, retaining a second plaintext store, and reporting every abort request as a confirmed stop. The trust and execution assumptions of [ADR-0164](0164-private-input-candidate-separates-native-storage-from-qualified-execution.md) remain; the queue qualifies one owning Host, not independent concurrently writing Hosts.

## Amendment: revocation erases values at once (#1521)

Revocation now deletes the revoked grant record inside the same account queue, right after the tombstone commits, instead of leaving the values for the next startup recovery. A failed delete is logged and still removed by recovery. The tombstone stays, so old version-one and version-two grants remain fenced, and a later private request for the same account creates a fresh grant. The Owner can list a PersonaBot's current accounts through `privateAccounts`, which returns declarations, status, the configured time and the configured card's IDs, never values or references.
