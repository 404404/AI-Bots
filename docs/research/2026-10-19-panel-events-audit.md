# Panel extension and Cordis Event audit

Date: 2026-10-19. Source: fetched `main`, commit `508e3b3c0`, inspected in an isolated worktree.

This is a static source audit, not an accepted architecture decision or a running-Host verification. No Host was launched and no tests were executed for this audit. Existing tests and historical verification guides below describe repository coverage, not a fresh runtime result.

## Findings

The Client already exposes an application-defined Panel Registry, but the repository does not establish a general public Cordis Event contract for every Panel's underlying domain changes. The two application-defined Host Cordis Event names found across production package sources are `botharness/personabot/activity` and `botharness/personabot/output-committed`. A Registry subscription, browser DOM event, authenticated SSE frame and Host Cordis Event have different consumers and lifetimes.

The DSH vocabulary explicitly separates the browser Cordis application from Host Services, and distinguishes a live Cordis notification from a durable SessionEvent. See [DSH Context](../../.agents/skills/dsh-plugin-dev/references/context.md) and [Decision Tree](../../.agents/skills/dsh-plugin-dev/references/decision-tree.md). BotHarness Panel, Global workspace and Channel workspace are application-defined presentation concepts in [CONTEXT](../../CONTEXT.md); presentation scope is not permission scope.

## Existing extension seam and authoring gaps

- The Client provides `dockPanels` and `channelSidebar` as browser Services: [Client entry](../../packages/client/src/client/index.ts), lines 416–419 and 459. Browser and Computer demonstrate separate Plugin consumers of `channelSidebar`; they do not demonstrate a public external SDK import.
- [dock-panels.ts](../../packages/client/src/client/dock-panels.ts), lines 15–41, defines `global | channel`, React component/header renderers and the current Channel context. Lines 54–69 expose registration, visibility controls and subscriptions. Lines 98–110 enforce unique ids and return a disposer that removes a registration and notifies listeners.
- [channel-sidebar.ts](../../packages/client/src/client/channel-sidebar.ts), lines 82–95 and 202–230, supplies `personabot | channel | both`, visibility predicates and a disposer. Non-settings entries feed the Dock Panel Registry.
- A `channel` Panel follows the active Channel; its props contain optional current `channel.id`, `type` and `botSlug`, not an independent binding to a fixed PersonaBot. `personabot` in the compatibility Registry means the current PersonaBot DM context. A fixed-Bot 3D companion would need a separately defined binding and data-access contract; it cannot derive that requirement from `scope: 'channel'` alone.
- [@botharness/ui package manifest](../../packages/client/package.json), lines 13–21, exports only `.`, `./client` and `./package.json`, with no `types` target or Panel SDK subpath. `DockPanel`, `DockPanelProps` and `DockPanelRegistry` are exported from the internal source file [dock-panels.ts](../../packages/client/src/client/dock-panels.ts), but neither package entry re-exports them. This is a static public-package-contract gap for external TypeScript authors.
- [ADR-0203](../adr/0203-bot-mode-is-a-dockable-layout-that-plugins-extend-with-dock-panels.md), “Making plugins easy to write” and delivery item 3, specifies an example Plugin, bilingual authoring guide and Skill. The current [todo source](../../packages/todo/src/index.ts), [Service](../../packages/todo/src/service.ts) and [Tools](../../packages/todo/src/tools.ts) are Host-side only. [Its manifest](../../packages/todo/package.json) has no Client contribution or Client export, and `packages/todo/src` contains no Client renderer. The advertised global to-do Panel example is therefore not present in this source tree. A dedicated completed Panel-authoring guide/Skill was not found in the inspected `docs` and `.agents/skills` trees; the architecture and ADR do document the Registry contract.
- Existing Client rebuild/HMR instructions are in [client-bridge.md](../client-bridge.md), section 7. They describe current development workflows and qualified shell behavior, not a completed Bot-owned install/reload authoring product. They do not prove arbitrary newly generated Panels can safely install and hot reload end to end.

## Public Host notifications found

### PersonaBot Activity

[core/plugin.ts](../../packages/core/src/plugin.ts), line 2525, forwards `core.states.onActivity` to `ctx.emit('botharness/personabot/activity', event)`; lines 2666–2669 declare the Cordis Event. [bot-state.ts](../../packages/core/src/state/bot-state.ts), lines 485–493, defines generation, revision, PersonaBot slug, aggregate state, change cause and optional safe activity, Session observations and attention.

This is a live projection notification, not a replayable domain event log. Activity currently covers Session/activity/attention changes; it does not imply an independently typed event for every change in schedules, memory, roster or runtime Providers. [ADR-0049](../adr/0049-personabot-activity-is-a-projection-with-live-events.md) describes the projection ownership. [tool-activity.test.ts](../../packages/core/test/tool-activity.test.ts), line 123 onward, includes a Cordis consumer listener.

Static robustness question: Activity uses plain `ctx.emit`, whereas Output explicitly isolates throwing/rejecting consumers. The [Output guide](../dev/guides/personabot-output.md) documents why plain emit did not isolate callbacks in the earlier pinned Cordis version. The current manifest pins Cordis 4.0.5, so the precise failure behavior of Activity consumers requires checking that version or a focused runtime test; this audit does not claim a reproduced failure.

### PersonaBot Output Committed

[channels/output.ts](../../packages/core/src/channels/output.ts), lines 5–21 and 54–77, defines `botharness/personabot/output-committed`, its version-1 public payload and isolated native listener dispatch. [core/plugin.ts](../../packages/core/src/plugin.ts), lines 1253–1254 and 630–635, wires the canonical Channel post-commit callback.

The producer checks explicit Session Ownership matches the author, emits frozen public fields, and separates each listener's synchronous/rejected failure. Draft model text, Human/system messages and writes without trusted origin are not PersonaBot outputs. Registration does not replay history. The [extension guide](../dev/guides/personabot-output.md), lines 7–19, demonstrates `ctx.on(..., { global: true })`, filtering by Bot/Channel and consumer idempotency by message id.

[personabot-output.test.ts](../../packages/core/test/personabot-output.test.ts), lines 46, 113, 150 and 174 onward, covers privacy allowlists, listener failure isolation, Fiber disposal, post-commit timing, retries, rollback and restart. The guide links an existing real-model QA script; it was not run in this audit.

Other Host Services may already call a capability on the provided `botharness` Service, but that is a Service dependency and query contract, not proof of a stable event subscription API.

## Candidate questions for the next design discussion

These are unresolved questions, not accepted decisions:

1. Which committed domain facts must independent Host Plugins observe? Enumerate facts and owning modules rather than requiring every UI interaction to emit an Event.
2. What initial query, generation/revision and reconnect behavior does each consumer need? A virtual office can read current Activity then subscribe; restart/reload behavior must not depend on notifications it missed.
3. Does a Panel follow the active Channel, bind permanently to one PersonaBot, or aggregate permitted Bots globally? Keep binding and access grants separate from placement scope.
4. Is the intended first authoring slice a trusted DSH code Plugin, or isolated untrusted content? Current React Registry registration executes in the browser application, so its contract does not supply an independent isolation boundary.
5. What is the minimal public type/guide/example surface, with one Bot-generated Panel that can register, observe one authorized fact, reload and dispose through existing DSH lifecycle? Define the observable end-to-end slice before expanding into many providers or panel types.
6. Which consumer failures must be isolated, and what bounded diagnostics will make bad listeners, reload failures and stale subscriptions observable?
