# Expo streaming rendering: decomposition and offload

Investigated 2026-10-18 for [#2028](https://github.com/BotHarness/DeepSeekBot/issues/2028) and [#1845](https://github.com/BotHarness/DeepSeekBot/issues/1845). This is an evidence inventory and experiment brief, not an adopted architecture or a 120 FPS qualification. The private original-text collection is `~/research/expo-rn-streaming-offload/`; originals are not redistributed in the repository.

## Version boundary

The checked worktree uses Expo 58.0.14, React Native 0.88.0, Reanimated 4.7.1, Worklets 0.13.0 and enriched-markdown 1.1.1. Its ordinary Android streaming prose uses `MarkdownText` and `FadingText`; the existing Enriched renderer handles unsupported Markdown. A dependency being present does not establish that the active prose path uses its native parser or animator.

The installed RN source contains prepared-text-layout support, but its feature-flag default is false. No runtime enablement was established. App config does not explicitly enable React Compiler; no compiled-output verification was performed. Neither is counted as a performance improvement.

## Offload contract to test

This is an application experiment proposal inferred from those boundaries, not a claim that the cited libraries implement it:

1. Keep canonical received text and the presentation cursor in their existing owners. Separate immutable completed blocks from the small active tail. Keep message-list identity independent of tail publication.
2. If profiles still show parser CPU blocking interaction, give one persistent Worker Runtime ownership of parser state. Send append deltas with a revision, allow one in-flight job and one replaceable latest pending state, and accept only matching results. Corrections, reference definitions, unclosed constructs, width/font changes and disposal need explicit reset rules. Do not drop canonical tokens when coalescing presentation work.
3. Send bounded block results back to RN Runtime; count transfer/serialization cost and stale-job work. [Worklets memory documentation](https://docs.swmansion.com/react-native-worklets/docs/fundamentals/sharing-memory/) describes copying, conversions and synchronization costs. Returning a complete document every tick can negate offload.
4. Measure animation separately. A diagnostic native tail-range fade can establish how much cost comes from animated React Text spans. It cannot ship as equivalent to the Human's requested staggered reading rhythm. A native grapheme/span animator would need its own selection, accessibility, Reduce Motion, Markdown-boundary and lifecycle validation.

Streamdown's inspected package develops against RN 0.85.3 and Worklets 0.10.2, requires remend 1.3.0, and documents [Bundle Mode configuration](https://github.com/software-mansion-labs/react-native-streamdown/blob/8bff19a6cb8f549c0ca4758618c398d9d056ac5c/README.md). Worklets documents RN 0.88 support for the 0.13 line, but that does not qualify the complete Streamdown/Enriched/SDK58 combination. Bundle Mode changes Babel/Metro and release packaging. Enriched's published compatibility table at the inspected revision stops at RN 0.87. Keep an integration build and device test as explicit gates.

An alternative native module can expose background parsing through Expo [AsyncFunction and queues](https://docs.expo.dev/modules/module-api/#asyncfunction). A synchronous JSI/native call still occupies its calling thread. A view AsyncFunction defaults to UI execution; choosing native code alone does not establish offload.

## Local measurements that constrain the next experiment

Release arm64, actual fixed 120 Hz, identical native APK entries, 21,492-character deterministic prose, 281 chunks/32 ms, order A B B A A B, three runs each. A is the existing bounded-layout implementation; B adds incremental Markdown and grapheme suffix reuse. Early and late are 2–22 and 22–42 seconds after trace start. Source timing lag was excluded from the source anchor. No real LLM calls were used.

| Median / 20-second window                 |      A |      B |
| ----------------------------------------- | -----: | -----: |
| Early combined JS-runtime CPU, seconds    | 17.402 | 13.083 |
| Early main-thread Choreographer p95, ms   |  5.879 |  6.840 |
| Early main-thread frames above 8.33 ms    |     13 |     34 |
| Late main-thread Choreographer p95, ms    |  5.491 |  6.831 |
| Late main-thread frames above 8.33 ms     |      3 |     36 |
| Early app-associated presentations/second | 84.632 | 85.418 |

The approximately 25% lower early combined JS CPU is not an end-to-end FPS improvement: native UI timings regressed. CPU is summed across threads named `mqt_v_js`; it is not a single-thread occupancy percentage. App-associated presentation rate includes intentional text pauses and is not continuous-scroll FPS. Platform FrameTimeline deadlines were around 20 ms even at 120 Hz; their low deadline-miss count cannot establish the 8.33 ms interaction budget.

A separate 48 ms publication-cadence pilot retained UI p95 around 6.84/6.92 ms and 33/37 frames over 8.33 ms. It did not improve the target and was reverted; one pilot is not a matched performance claim. A native animation-clock prototype and removing a constant `top: 0` also failed to establish an improvement and were reverted.

Computer-injected gestures later failed in system logs despite ADB exit 0. The Human confirmed physical scrolling works. A subsequent 20-second manual capture contained no observed scroll changes or app presentations; it is not a valid scroll test. Do not claim a gesture regression in the app or stable 120 FPS from these samples.

Public techniques need the same Release device replay plus observable scroll movement, main-thread execution, presentation intervals, memory, queue age and semantic completion. The [original Reanimated fast-path PR](https://github.com/software-mansion/react-native-reanimated/pull/7823) reports emulator Debug gains; those numbers do not qualify this physical Release workload.

## Investigation stop and open work

Two independent primary-source searches returned. The first followed Fabric documentation into Fiber scheduling and FlashList item rendering; the second followed Worklets into Streamdown, Enriched, md4c and the original fast-path change. The parent archived originals and followed Streamdown's Bundle Mode link and Enriched's parser link. Each research question now has a concrete original-text location; applicability gaps remain explicit rather than inferred as passes.

No public SDK58/RN0.88 Android 120 Hz streaming qualification was found for the proposed combination. Skia selection/accessibility tradeoffs, custom native grapheme animation and incremental remend semantics were not qualified. No dependencies, compiler switches or native performance flags were enabled by this research.
