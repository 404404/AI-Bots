# ADR-0173: Group behavior items resolve by ID with explicit Deny

Date: 2026-10-11
Status: Accepted
Issue: [#1423](https://github.com/BotHarness/DeepSeekBot/issues/1423)

The Human accepted reusable behavior permission items so Group assignment can share natural-language behavior without composing several free-form Roles. This extends ADR-0168's structured-only first tracer: each paired person keeps one primary behavior Role, and Messaging owns Bot-scoped named items in the Operational Database. Groups reference stable IDs, not copies of text. An item's latest canonical revision and all current group sources are resolved on demand; duplicate Allows yield one item, while any explicit Deny yields a prohibition with a visible Allow/Deny conflict when both effects exist. Primary Role constraints remain applicable and Group Allows cannot widen them.

This deterministic algebra concerns item identity/effect, not proof that arbitrary texts are consistent or enforcement of mail, files or Shell access. Existing Host management capabilities and delegation stay independently checked. Group membership keeps the exact current Bot/App pairing fence; revoke/re-pair does not inherit memberships. The first slice qualifies same-ID overlaps/conflicts, settings previews and current-permission results before Human feedback gates semantic/declared-mutual-exclusion variants or other Providers.

Generation 81 adds one item table; existing records default to no behavior-item references. Group selections pin current item revisions at the write boundary; item edits use their own expected revision and show affected people. Deleting a referenced item is refused until every Group reference is removed, avoiding dangling or copied policies. Authenticated settings reuse the existing API Gateway/Client senderAccess commands, and the model reads the existing bridge_sender_permissions result; no second Provider Consumer, permission cache or native DSH RBAC is added. Client previews share a pure ID/effect resolver but are dated UI evidence; Host current queries remain authoritative.

Back up before upgrade. An older writer cannot reopen generation 81; rollback requires the pre-upgrade backup or a compatible forward repair. Natural-language behavior remains model guidance. Reliable hard resource restrictions and arbitrary semantic analysis require their own reviewed and qualified slice.

## Declared exclusions — second slice, 2026-10-12

The Human selected authored mutual exclusion and incompatible-edit gating as the next #1423 slice after accepting the first tracer. A Behavior permission item may reference other stable IDs in the same Bot. One declaration is bilateral: changing either endpoint updates both records and their changed revisions atomically. Endpoint revision checks prevent a stale dialog from overwriting newer metadata; deletion removes unused reciprocal links and advances the surviving revisions. No new schema/table, Provider or runtime authority is introduced.

The shared pure preview checks final effective Allows. Same-ID explicit Deny retains precedence, so a denied endpoint does not contradict an allowed endpoint. Incompatible pairs name both items and all source groups; multiple independent Allow sources must all be resolved. Each group's own configuration is checked even with no members. Combined group contributions are checked for every currently approved ordinary pairing at its exact Binding. Disabled bindings are included in configuration validation so restoring reception cannot expose a latent incompatible assignment; current runtime capability queries retain their existing availability fences.

Messaging validates the proposed final item/group configuration within its existing canonical transaction, before any write. Item relation edits, group grants/member additions, Deny removal, member removal from a Deny group and group deletion cannot introduce incompatible effective Allows. Removing an Allow source or explicitly denying one endpoint is a valid resolution. Client previews and disabled Save buttons guide the Human; direct/stale API calls meet the same Host refusal and leave policy/group/item revisions unchanged. Text-only edits still preview affected people, but the system does not infer contradictions from free-form text or arbitrary primary Role instructions.

Bilateral links make the interaction editable from either item and avoid a hidden directional owner; an exclusion is not a priority order and never silently chooses one group's text. Current sender permission lookup projects out configuration-only exclusion IDs, retaining the primary Role, item revisions, effective effects and current sources without granting management/delegation rights. An exclusion does not prohibit an otherwise effective Allow: native QA exposed that ambiguity when the model received authored metadata beside the resolved policy. Settings retain the metadata for deterministic editing. A downgrade to a writer that does not understand these declarations would bypass mutation gating; stop policy editing before rollback and preserve/restore the compatible configuration instead of trusting an older writer. Native QA and Human feedback qualify this new slice separately from the accepted same-ID flow.
