# Mobile UI/UX rules

This is the target design of the DeepSeekBot mobile app. Every new or changed screen follows it. Tokens and theming are in [ADR-0201](../../docs/adr/0201-the-mobile-design-system-maps-web-roles-onto-native-components.md); this file covers structure, screens, components and code rules.

References:

| App       | What we use from it                                                                                                                                                                          |
| --------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Manus     | The chat: one Bot is one contact, the conversation reads like IM, and action cards sit in the chat.                                                                                          |
| Grok Bot  | Bots and group chats in one list, with separate "needs you" and "new result" states. Approval cards with **Allow once / Always allow / Deny**, and the Human taking over the Bot's computer. |
| Meta Muse | A Bot profile whose identity and memory are visible and editable.                                                                                                                            |

## Overlay contract

[Mobile overlay standard](./OVERLAYS.md) ([中文](./OVERLAYS.zh.md)) defines presentation choice, handle/header/body anatomy, immediate versus transactional changes, dismissal, platform differences and acceptance gates. It is the target contract for new or changed overlays; its audit records current gaps, including the provisional iOS Settings fix in #2112.

## Native first

On both platforms the system's own design and components are the standard: Apple's Human Interface Guidelines on iOS (`ios-hig` skill), Material 3 on Android (`android-material` skill). Where the platform has a component for the job, use it (native navigation, `@expo/ui` SwiftUI views on iOS, `@expo/ui` Jetpack Compose views on Android) and keep its default look and behaviour; do not draw a React Native look-alike or restyle it into a house style. A custom surface is allowed only where no native component fits, and its reason is written in this file first.

Older rules below that prescribe a custom surface where a native component exists describe the current implementation, not the target. Change them to the native component when the screen is next touched, and update the rule in the same change.

## Application dialogs

- Application-owned confirmations and choice menus use `showAppDialog` (or `confirmDestructive` / `showActionMenu`) and the root `AppDialogHost`. Do not call React Native `Alert.alert` directly from a screen or feature. Per Native first, iOS shows system alerts (menus follow [iOS menus and native controls](#ios-menus-and-native-controls)), and Android shows the Material 3 `AlertDialog` from `@expo/ui/jetpack-compose`, themed by `seedColor` = accent. Operating-system permission prompts, photo pickers and the share sheet remain system-owned.
- A confirmation puts Cancel in the dialog's dismiss slot and the action in its confirm slot as text buttons; a destructive action's label uses `danger`. A menu with no anchor (a long press, `showActionMenu`) is never a dialog: on Android it is a Material 3 modal bottom sheet listing its title and one `ListItem` per command, a divider before the destructive command in `danger`, dismissed by Back, scrim or swipe. A menu from a ⋯ button is an anchored dropdown (`ActionMenuButton`), with the same divider before its destructive item. A confirmation always states the consequence in its message, not only a title. Destructive menu choices open a second confirmation describing the consequence. Back and a tap outside dismiss without choosing. The system dialog handles width, scrolling at large text sizes, focus and TalkBack.
- While an asynchronous action is pending, disable repeat submission and dismissal; close after success. On failure, keep the prompt and retry available. A menu opening a confirmation must not dismiss the newer prompt when its old callback finishes. Dialog requests are transient UI state, never a second persistence or authorization owner.
- Native checks include cancel/button/Back/backdrop paths, nested confirmation, light/dark and default/intermediate/maximum text. Verify the original pairing/group remains unchanged after cancellation, keyboard dismissal from focused search, and the actual rendering above an open drawer or profile. Record iOS and TalkBack qualification separately.

## iOS menus and native controls

This applies [Native first](#native-first) to iOS menus, following the Apple HIG (the `ios-hig` skill maps each component to our stack). Build them with `@expo/ui` SwiftUI views or native navigation, not with React Native views drawn to look like them. On Android the same jobs use Material 3 components: a dropdown menu for ⋯ actions, an exposed dropdown menu or radio dialog for a single choice, and a Material dialog for confirmations.

- **Action menus are native pull-down menus.** A ⋯ button opens a SwiftUI `Menu` anchored to it; a long press on a row opens a native context menu with the same actions. Items are commands with title-case labels, most-used first, related items grouped, at most one submenu level. Destructive items carry the destructive role and still open a confirmation describing the consequence.
- **Choices of one value are native pop-up menus.** A short, fixed set of mutually exclusive options shows the current value on the control and opens a menu-style picker with a checkmark on the selection. Two to five peer modes that should stay visible use a segmented control (`Segmented`), with a one-word label per segment; a label that needs more words means the choice belongs in a menu or a list instead. Options that need explanation, search or a long list use a sheet.
- **Alerts are for confirmations and errors only.** A system alert asks one question with a Cancel and at most one or two actions; it never lists a menu of unrelated commands.
- **Exceptions stay as recorded.** App-owned tab presentation (ADR-0235) is a deliberate custom surface. Any new custom surface where the system has a control needs the reason written here first. The chat bubble menu is a native bottom sheet (see Chat), not a custom surface.
- Native menus inherit Liquid Glass, Dynamic Type, VoiceOver and Reduce Transparency from the system; do not restyle them. Every action in a context menu is also reachable from a visible control or an accessibility action.

Build a ⋯ menu with `ActionMenuButton` (`src/ui/primitives/action-menu-button`): a SwiftUI pull-down `Menu` with SF Symbols on iOS and a Material 3 `DropdownMenu` on Android, both anchored to the button. The Host drawer and the group member ⋯ menus use it. Long press on a row still opens `showActionMenu` (an action sheet on iOS).

## Activity query controls

- Activity has two header entries: **Filter and sort** and **Search Activity**. Sorting is part of the same options sheet as category, unread-only, Bot and conversation filters.
- iOS uses native navigation toolbar buttons: the system supplies Liquid Glass on iOS 26 and its supported appearance on earlier versions. Active search uses a native input in a measured floating surface outside the fixed-height navigation bar, so accessibility text can grow without clipping. Android uses opaque Material-style icon actions and its native text input.
- The iOS options sheet uses system page-sheet presentation with swipe dismissal, inset grouped rows and trailing checkmarks. Android uses the modal bottom-sheet surface, leading radio indicators and system Back dismissal. Unread-only uses a native switch on each platform. Long option lists virtualize and scroll; footer actions remain reachable.
- Options apply immediately and remain selected after swipe dismissal or Android Back; there are no Cancel/Done actions. Reset all immediately restores default ordering and the Needs you tab, with all Bots/conversations and unread-only off. Search is independent of this reset. The iOS search surface reserves equal outer gutters; iOS search keeps its built-in clear control; tapping blank list space dismisses search without a second close button and preserves the query for reopening. The focused Activity screen owns status-bar contrast for its current appearance.

References: [Apple toolbars](https://developer.apple.com/design/human-interface-guidelines/toolbars), [Apple sheets](https://developer.apple.com/design/human-interface-guidelines/sheets), [Material bottom sheets](https://m3.material.io/components/bottom-sheets/guidelines), [Android radio selection](https://developer.android.com/develop/ui/compose/components/radio-button).

## Chats source navigation (#2194)

Chats uses the same canvas and left-aligned title treatment as Activity. The title/chevron opens the workspace drawer; Settings remains on the right. Directly below, a reusable native pager presents a horizontally scrolling **All → Computer → Organization** strip. Selecting a tab or swiping the list changes only the device-local browsing scope. Stable directory order, including empty member Organizations and channel-only guest Organizations, is independent of message arrival. Labels use local Computer names; keys retain full source/account identity. Each tab stays on one line with a bounded width and tail-ellipsized label; the source icon never shrinks. Service URLs do not add a second line. Full source/account identity remains in accessibility labels and the source drawer.

This first slice retains one active Computer plus authorized Organizations. It does not implement simultaneous multiple-Computer connections. Search and creation remain in their existing list-header placement until #2195/#2196. Activity inherits scope and keeps action/replies/unread paging; unsupported Cloud scope has an explicit notice and no borrowed Computer badge. All discloses that Cloud activity is not yet included. Source-owned history, credentials, drafts, permissions and send paths stay unchanged.

The older Host-band description below records prior presentation/customization behavior. The Chats Header and environment selector above supersede that entry layout; saved Computer customization remains available in the drawer.

## Structure

The shell is set by [ADR-0211](../../docs/adr/0211-the-mobile-app-has-two-tabs-with-settings-and-hosts-in-the-header.md): what the Human does most sits under the thumb, and what they do rarely sits in the header.

- **One workspace drawer, two connection types.** Computers are paired Hosts; cloud workspaces belong to an explicitly trusted TOB instance. The existing left drawer is shared across both, with Computers and Cloud tabs. Cloud headers expose the same workspace switcher. A guest sees the organization initial/name and “invited channels only”; selecting it shows only current channel grants. Instance domains disambiguate identically named workspaces. The contextual join/pair action stays below the tabs; the directory scrolls between that header and a fixed footer.
- **Computer workspaces.** Each paired computer is a Host.
  - The app stays connected to every paired Host at once.
  - The Chats list and every chat show one Host at a time. The Chats header has a Slack-style band in the accent colour (a muted accent in dark mode); the list sits on a panel with rounded top corners below it.
  - The **Host chip** at the top left shows the Host's initial tile, its name and ▾. Tapping it opens the shared **workspace drawer**.
  - **Customize computer** sets how each Host looks, kept on the phone per Host. It is a form sheet with a live preview of the band, opened from that Host's ⋯ menu in the Host drawer (or a long press on its row), so each paired Host is customized where it is listed.
    - Name: a local name shown in the Host chip and the drawer instead of the Host's own name; clearing it goes back to the Host's name.
    - Avatar: the initial tile (default), one of eight pixel portraits from the PersonaBot avatar generator, or a photo cropped square.
    - Banner: the accent band (default), a solid colour (ten swatches or a typed hex), a two-stop gradient (six presets or typed stops), or a picture under a dark scrim.
    - A custom colour goes through the accent band's steps, so dark mode mutes it the same way. The ink is white or near-black, whichever reads on every stop; a picture always takes white ink with a soft shadow.
- **Workspace drawer** switches between paired Computers and Cloud organization workspaces. It slides in from the left, covers about 85% of the width and dims the list behind it.
  - On iOS 26, unless Reduce Transparency is on, it is a floating Liquid Glass sidebar: inset `sidebar.inset` from the screen's left, top and bottom edges with `sidebar.radius` corners concentric with the display. Its rows are clear; a pressed row and the current Computer or workspace show a `radius.lg` highlight inset from the sidebar's edges, as iOS sidebars do. The pairing card is frosted. A Computer's ⋯ opens a native pull-down menu anchored to it (Customize, Show this computer, Unpair); a long press on the row still opens the action sheet. Older iOS, Reduce Transparency and Android keep the opaque full-height drawer.
  - Rounded **Computers / Cloud** tabs are the first row above one scrolling list, with no duplicate title or close button. Opening the drawer selects the current route's tab; switching tabs only changes the list, never the active computer or cloud session. Android uses opaque raised chips; iOS uses the existing glass material with Reduce Transparency, older OS and large-text fallbacks. Tabs expose their selected state to accessibility.
  - One contextual plus action sits directly below the tabs, above the scrolling list: Computers opens **Pair a new computer** directly; Cloud opens **Join by link or QR** directly. There is no mixed action chooser or stacked icon group. Organization creation and service configuration live under **Manage cloud services** on the Cloud tab; Notifications stays at the bottom of a fixed footer on both tabs; Cloud service management sits above it. Only the directory scrolls.
  - A cloud service is an instance/address; its organization is a cloud workspace; a channel belongs to that organization. An invitation already identifies its service and scope: workspace membership or access to only one channel. The existing preview and acceptance flow keeps this distinction explicit. No separate server-selection step or new authorization store is introduced.
  - Each Host row has its Computer avatar tile (the same tile as the Host chip; the current Host's tile has an `fg` ring at radius `lg`, concentric with the tile, as Slack marks the current workspace), its name, an online/offline/checking dot and label, then one **count chip** on the right (see Count chip below). It shows **Needs you** when anything waits for the Human, because that matters most; otherwise it shows **Unread**, the count of unread conversations. A ⋯ button at the end, or a long press on the row, opens the Host's menu: Customize (name, avatar and banner), Show this computer, and Unpair, which asks for confirmation. The ⋯ menu is the system's own anchored menu: a SwiftUI pull-down on iOS and a Material 3 dropdown on Android, with Unpair in the danger colour.
  - The Host chip opens it, and so does a swipe right from the left edge of a tab's root screen. The edge swipe is never attached inside a pushed chat, where it stays the system Back.
  - Tapping a Host switches to it and closes the drawer. Tapping the backdrop, swiping left or using the accessibility escape gesture closes it. Opening focuses the selected tab.
  - It takes screen-reader focus when it opens and returns focus to the Host chip when it closes. With Reduce Motion on it appears without sliding.
  - Android Back closes it. Android draws the same drawer.
  - Normal-size rows use a name and a smaller muted address, with one line each. Accessibility sizes may wrap. Status dots and accessible labels retain online/permission context; channel-only guests keep the invited-channel scope in their secondary label.
  - Pairing accepts an optional local name using the existing computer appearance store; direct-link pairing can keep the original name, then rename in Customize computer. Cloud import accepts a display name; Manage cloud services can rename it later. These names affect only this phone and never change Host identity, organization names, trusted endpoints or sessions.
- **Tabs** remain **Chats** and **Activity**, using the same Expo Router JS tab navigator on all platforms, with the existing route stacks above it. Search arrives with its working N3 slice.
  - A chat or creation form is pushed above the tabs, hiding the bar. Each list reserves the measured bar height plus safe-area gap; scroll hide/reveal stays on the UI thread.
  - The floating navigation island sits beside a separate circular **+**, equal-height at default text size. At larger text sizes, the island can grow; on iOS each tab label stays on one line and shrinks to fit (`navigationBar.labelMinScale`) instead of breaking inside a word; the icon-only circle keeps its normal touch size and aligns to the bottom so it does not consume the labels' width. iOS uses real SwiftUI navigation and plus/close buttons. On iOS 26 the selected tab and circular action use native glass button styles over the shared glass island; earlier iOS uses bordered controls. System Reduce Transparency remains authoritative. Native text keeps semantic Dynamic Type. This is app-owned tab presentation, not `NativeTabs` or a second navigation stack (ADR-0235).
  - Android retains the opaque OCAT raised rounded rectangle, hairline edge, faint token shadow and selected icon tile. The Activity destination shows the bell **or** the capped pending count, never both, on iOS and Android alike: when Activity is not selected and something is pending, the count replaces the bell; when nothing is pending, or Activity is selected (its feed already shows the items), the bell returns. Android cross-fades the swap. The accessible label always carries the count. Essential labels grow with system text.
  - **+** opens a modal action panel in the island position, with close in the circular position. Back, accessibility escape and backdrop only dismiss it. The panel is always a scrollable vertical menu: each full-width row has a leading icon and left-aligned wrapping label. Target choices use the same row treatment. On iOS 26 the panel uses a native rounded-rectangle glass backdrop, including at larger text sizes; Reduce Transparency and older iOS keep an opaque raised surface. This panel opt-in does not change the existing multiline drawer-title fallback. Android retains its opaque OCAT surface. The panel still uses the existing modal fade, not a native glass morph transition.
  - Computer: new Channel/new Bot. Owner Organization: new Channel/invite. All: new Channel/new Bot/join with link or QR, followed by explicit destination choice where needed. Member/guest workspaces do not gain owner controls. Pairing and Organization administration stay in the drawer.
  - Creation binds the chosen Host ID or cloud account scope plus Organization ID. Cloud rechecks current identity and ownership before opening/submitting; stale scope refuses. Existing Host full-client and CloudClient idempotent mutations remain the business owners. Dismissal never starts a background operation.

- **Chats** shows the current Host:
  - Conversation rows keep the title and timestamp on one horizontal line at every system text size. The title takes the remaining width and truncates with tail ellipsis; the timestamp keeps its own single-line slot. Preview/status and count stay on a second line. A conversation without a timestamp does not reserve an empty metadata line. Preserve native font scaling and the complete accessible title/preview.
  - The header has a compact Host title on the left and a Settings gear on the right, on both iOS and Android. This row stays horizontal at every system text size: the Host chip shrinks, its name occupies one line with tail ellipsis, and the Settings target stays at the trailing edge. Keep native font scaling and the full accessible Host name; both targets retain the platform minimum touch size. Other Host-name presentations may wrap. The Host picker stays mounted between visits; its translation follows a critically damped UI-thread spring and its scrim is clamped. Hidden contents leave the accessibility tree.
  - **+** sits at the right of the channel search field. It opens the native **New PersonaBot** / **New Channel** menu and uses the app's create flow, or the full client where the app has none yet.
  - A **search field** floats just above the bottom navigation island, within reach of the thumb, as iOS 26 places search. It is a capsule on the shared navigation glass (`DrawerMaterial`; opaque raised on older iOS, Reduce Transparency and Android) inset like the island, rides above the keyboard while typing, and hides and returns with the navigation on scroll. While it is focused or holds a query the navigation stays visible, and a circular close button beside it (the island's glass circle) clears the query and dismisses the keyboard. The field is a native UIKit text field with the system clear button, not a SwiftUI field, which has none. The list reserves the field's height under its last row. There are no shortcut cards: Activity already gathers what needs the Human.
  - On Android, swiping a Computer conversation row left reveals Material 3 list actions as 56dp icon buttons with 16dp corners: Mute or Unmute (on this computer), Pin or Unpin, and, when it has unread messages, Mark as read as the end-aligned primary action in the accent colour. They use the existing Host methods (`channelMuteSet`, `rosterBatch`, `channelMarkRead`; CLI `channel-mute`, `roster-batch`, `channel-mark-read`). The same actions are accessibility actions on the row, so TalkBack reaches them without the swipe. Cloud rows have no swipe actions yet. A full swipe does not trigger an action.
  - One list of PersonaBot DMs and Channels together, grouped by the Host's **Channel sections** as on the desktop sidebar:
    - Sections come in the desktop's order. Ungrouped DMs and Channels sit between them in the desktop's top-level order.
    - A section header shows its name and Channel count and collapses or expands on tap. A collapsed section still shows a "Needs you" mark when something inside needs the Human. The collapse state is kept on the phone, per Host.
    - Hidden Channels stay out of the list. Pins and the sort mode follow `CONTEXT.md`.
    - Changes made on the desktop show when the roster refreshes. Creating, renaming, reordering and moving Channels between sections stays on the desktop for now.
    - A Host with no sections shows one flat list by latest activity.
- **Search** finds a PersonaBot or Channel on the current Host:
  - Typing in the Chats search field filters the list in place, as chat apps do; there is no separate search tab.
  - It matches PersonaBot display names and Channel titles on the device, ignoring case and full-width forms, with names that start with the query first. Hidden Channels stay out. A DM result opens its chat, and a Channel result opens that Channel's chat. When nothing matches it says so. Message full-text search is not part of it.
- **Activity** is the Human Inbox across Bots on the currently selected Host:
  - Three pinned, underlined tabs are Needs you / For you / Other unread. Needs you is selected on entry and groups tool approvals, formal questions and private input. All and handled history remain available through the category filter. Other unread uses the Host's Channel summaries; Bot filtering is also calculated by the Host, not by the summary's last author.
  - Three equal-width tabs each center the icon and label as one group. Only the selected tab shows its decorative leading icon. Its underline fills that entire third of the strip without outer gutters and follows the page's swipe position. Use `react-native-tab-view` with Expo-compatible native `react-native-pager-view` for horizontal page gestures, including gestures starting in the feed or empty state; keep each page's virtualized list mounted after its first visit so its vertical position survives switching. Previous Activity collapse preferences do not hide content. Labels retain native system scaling and wrap within their third at large text. Switching pages preserves search, sort, Bot and conversation filters. All/handled filters temporarily show that category in the current page without a selected top tab; selecting or swiping to another tab resumes its category. Tabs remain selectable during loading or error. Respect reduced motion for programmatic transitions.
  - Bound list summary previews and their accessibility labels before passing them to native Text; a two-line preview must not measure an entire long reply. Keep the original item for opening its conversation. Loaded action-card ports keep their identity across page re-renders so returning to a page retains its loaded content and draft instead of flashing a loading card.
  - Keep all three decorative tab icons mounted. Derive their opacity, subtle scale and icon/label group translation from the same continuous native pager position as the underline, so the incoming icon appears during a drag and reverses when the drag is cancelled. At rest, the selected icon/label pair is centered; inactive labels are centered alone. Avoid selection-triggered mount animations and per-frame React updates. Reduced motion uses settled icon states without the morph transform.
  - Approvals, questions and folder requests can be decided in place, on the same cards as chat. Auto-rejected calls (Allow once), group join requests (Accept / Decline) and Assignment asks (reply that carries the Assignment target) open a native detail with the same card. Private input retains its full-client route: its chat card and Inbox detail open the full client at that request.
  - Posts and rows are separated by space and layer fills, not divider lines.
  - A row's title is `category · Bot`; a reply keeps its text on a second line, and a handled item collapses to one line: `category · Bot · summary`.
  - Opening an item jumps to the card in its chat; an unread conversation opens its DM or group chat.
  - A floating header follows the chat chrome: title on the left, sorting, filtering and Activity search on the right. Filters live in a sheet, with category, Bot, Channel, unread-message and clear controls; no permanent filter chips. A nonblank Activity search hides sections with no matches; an entirely empty result shows one no-results message. Clearing the query restores normal empty sections. Sections with another page remain reachable. Search uses safe Activity summaries and Channel/Bot labels on the current Host before pagination. Handled history stays excluded unless selected. Default ordering is oldest action first, mentions before other personal messages, then newest unread conversation; explicit newest/oldest overrides personal-message priority. Each section can load another bounded page. Hosts without query version 1 show an update error. Complete tab totals remain a subsequent slice of [#1954](https://github.com/BotHarness/DeepSeekBot/issues/1954); when another page exists, the screen identifies counts as loaded items.
- **Settings** opens from the gear as an immediate-settings sheet: one handle, fixed header and scrolling body; swipe or activation of the handle dismisses while completed settings remain. Child pages use Back within the same sheet. Android retains its fixed accessible handle, large detent and 28dp top corners. On iOS, native modal presentation keeps nested content visible; the shared frame supplies one handle in the native vertical dismissal region, and the native header owns only the root title. The handle is also a Close button with a platform-sized touch target, explicit accessibility activation and escape; no extra X is shown. Child Back still pops only one page. Actual screen-reader focus and gestures require separate native acceptance. There is no Done/save step for immediate preferences. Settings reuses row and section components, in groups. Each navigable or action row leads with a system icon (`RowIcon`: an SF Symbol on iOS, a Material Symbol on Android), monochrome `fg`, or `accent`/`danger` to match the row's tone, so a row's purpose reads before its label:
  - **Models and presets** configures this Host's existing global default model and shared Model Preset library. Bots without an override follow that default. Presets can be created, renamed and edited for Orchestrator, Assignment default, allowed Assignment models and reasoning effort, through the existing Host methods. Editing a preset does not rewrite Bots that already applied a copy. Model selection pushes inside the same drawer, searches model/provider names and IDs, virtualizes the catalog, and keeps missing-key models visible but unavailable for selection. Saved settings and read errors are scoped to the Host and Bot/preset; cached content remains visible during refresh or failure, with retry.
  - Android groups use `androidSettings` tokens: 28dp corners, 16dp row padding, 56dp minimum single-line rows and 72dp minimum supporting rows that expand with system text. Section headings use the accent role, supporting text uses the body ramp and muted role, and separators are inset 16dp. Selected choices use the layer's chosen fill plus accent text and the existing checkmark. Explicit navigation rows show a chevron; destructive and copy actions do not imply navigation. Android switches use SDK 58 Expo UI's native Material 3 control inside a bounded Host; state and persistence remain owned by existing preferences. iOS retains its existing rows and switch adapter.
  - **Usage** comes first, as one card for the current Host, like a fitness app's week: "Usage", "Last 7 days" and a chevron, the 7-day token total in `display`, and a bar per day (`DayBars`). An idle Host shows a quiet week of stubs, and a failed read shows a danger line with Try again under the card. Tapping it pushes the **Usage** screen:
    - A Today / 7 days / 4 weeks / 12 weeks `Segmented` switch; switching reads the Host again. A background 4-week read checks support on entry; until it succeeds, and on older Hosts, only Today and 7 days appear. An `invalid-input` refusal of a longer period returns to 7 days without showing an error. The Settings card does not probe or change its 7-day range.
    - The period's dates, its total, daily bars for 7 and 28 days, and 12 weekly bars for 84 days. Each week starts at the range's first day, not a calendar-week boundary; a selected weekly bar shows its date range and partial-aware total. Longer charts omit cramped weekday labels, retaining their dates in the chart's accessibility label. A muted note explains when some usage could not be counted or is still being counted.
    - Like the Health app, tapping a day's bar shows that day: the date and its tokens replace the week's dates and total, and the other bars dim to `chart.dim`. Tapping the same bar again, or switching the period, shows the week again. `DayBars` takes `selected` and `onSelect`; without `onSelect` (the Settings card) the bars are not tappable.
    - **By kind**: Input, Output, Cache read and Cache write. **By PersonaBot**: avatar, name, share of the total and tokens; tapping a current Bot opens its profile, a deleted one reads "Removed". **Memory activity**: each Bot's Memory changes for the week with a small bar per day. Both lists page with Show more.
    - Everything comes from the Host's `overviewUsage` and `overviewMemory`, the same reads as the Web Client's activity view; the card's week total matches its week total.
  - **Connections**: the current Host and its connection status, Computers (paired Hosts, their status and unpairing, with the same confirmation and error notice as before), Notifications, and Open full client.
  - **Interface**: App icon (the full DeepSeekBot portrait ships as the default icon; the chibi portrait is the alternate; both have dark and tinted variants on iOS), and Appearance (scheme, accent, chat wallpaper) once it exists. Each Host's name, avatar and banner are customized from its menu in the Host drawer, not here.
  - **Chats**: Channel sections and Hidden Channels, each pushing its own screen.

## Sheet and drawer surfaces

- `theme.overlay.fill` is the default background of sheets and drawers, derived from the canonical `sheet` colour. Handle area, header and scrolling body share that opaque fill; scrolling containers stay transparent. Do not substitute `base` or `surface` for part of the same overlay.
- `theme.overlay.handle` mixes 38% `fg` into that fill. It is a quiet decorative grabber, not a text colour. The Android Close action retains the platform's 48dp touch target; iOS retains its native grabber.
- Cards and grouped rows inside a sheet use `raised`; pressed/selected states come from that same layer. Accent colours express actions or selection rather than tinting the entire handle/header.
- Native form-sheet routes use `sheetScreenOptions` and `SheetScreen`. The shared frame owns the Android handle and continuous background; the route options own detents and corners. Lists remain virtualized and enable nested scrolling so the native sheet keeps content-before-dismiss gestures. Fallback modal editors use the same overlay tokens; a grabber is allowed only when its indicated drag behavior is implemented and verified. Existing decorative-only handles are migration gaps, not an approved pattern.

## Screens

**Conversation row**

- On the Activity and Chats root lists, deliberate downward content scrolling hides the global bottom navigation; upward travel or reaching the top restores it. Clamp elastic overscroll so bounce does not toggle chrome. Activity also collapses its title/filter/search row, leaving the three tabs pinned below the safe area; no gradient covers rows beneath the tabs. Searching and filtering keep controls visible. Page changes restore chrome without discarding each page's scroll position. Scroll intent and transforms run on the UI thread; only native visibility/accessibility boundaries cross to React. List geometry stays fixed during the animation.

- A 48pt avatar: the Bot's avatar as a rounded square (`radius.md`), or a rounded square with `#` for a Channel. A paused Bot's avatar is dimmed.
- First line: title, IM channel badges and time. The time follows IM lists: the clock time today, then Yesterday, the weekday within the last week, month/day this year, and the full date before that.
- Second line: the latest message as a one-line preview, in `fg` while the conversation has unread messages, then one status glyph at the trailing edge, the same set as the desktop sidebar: a spinning arc while the Bot thinks or works (still under Reduce Motion), a `warning` ring when it waits for the Human, a `danger` mark when blocked, a filled check when it finished and the Human has not read it, a `muted` check when it finished within the last day, and a `muted` moon when paused. Idle rows and Channels show none.

  - The routine sheet is titled with the routine, its trigger and next run as the subtitle. **Run now** (primary) and **Pause** / **Resume** (secondary) sit side by side, then the instruction, **Recent runs** (the last five: run now or scheduled, and its state, with the time), and a group with **Edit** and **Delete** (red).
  - Delete asks in place ("Delete “{routine}”?", Cancel and a danger Delete); nothing is removed before that.
  - **New routine** and **Edit** turn the sheet into a form: Title, Instruction, then **When** as chips (Daily, Weekly, Every few hours), the time or the hours between runs, weekday chips for Weekly, and the time zone as a footnote. **Next runs** previews the Host's next occurrences (up to five) as the form changes. Save stays disabled while the form is incomplete, and a footnote names what is missing.
  - A routine whose trigger the phone cannot express (minutes, once, cron) shows that note, and Edit opens the full client.
  - A refusal from the Host shows in a `danger` callout in the sheet.
- Identity and Memory stay read-only for now; editing them from the phone comes later.

## Layers and states

Every fill comes from a layer, like the Web Client's DSH layers. `theme.layer.<name>` holds opaque colours:

| Layer    | Fill (DSH)           | Used for                                                  |
| -------- | -------------------- | --------------------------------------------------------- |
| `canvas` | `bg-base`            | screens, lists, the chat behind the composer              |
| `raised` | `bg-module-platform` | cards, Bot bubbles, shortcut cards, the Android composer  |
| `well`   | `bg-base`            | a recessed area in a raised card: option groups, previews |
| `field`  | `bg-layer-1`         | text inputs in a card, edged with `border-l4`             |
| `sheet`  | `bg-layer-2`         | settings rows on a screen, and menus                      |

Each layer has `fill`, `pressed`, `selected` (neutral, such as the current tab), `chosen` (the Human's pick, an accent tint), `danger` (a destructive button, a red tint), `inset` (code, badges, tiles), `edge` and `divider`.

- `chosen` is the accent over the fill, 13% in light and 30% in dark. On `well` it equals DSH `state-business-tertiary`, and it follows a Bot's accent.
- A state is pushed further from its fill until it stands apart from the fill, the layer under it and the other states (`SEPARATION` in `layers.ts`; `test/design-tokens.test.ts` checks every scheme and accent). DSH's dark `interactive-bg-active` over `bg-base` equals `bg-module-platform`, so without this a selected row in a card looks like the card.
- Buttons are solid pills (`radius.round`) with no border, and take their colours from `buttonColors(theme, tone, on)` (`controls.ts`) for the layer they sit `on`. Primary is the neutral `fg` fill with a `base` label, never the Bot accent. Secondary is the layer's `selected`, or the next layer's fill when `selected` is too close to the layer. Danger is the layer's `danger` tint with a red label. Each fill stands apart from the layer and from the other tones, and each label reaches 4.5:1.
- Bottom sheets (`chat/sheet.tsx`) follow the [overlay contract](./OVERLAYS.md), with one functional handle, task-specific header actions and `theme.overlay.fill`. The existing fallback Close/grabber implementation requires caller-by-caller migration. Their content is iOS-style inset groups on `raised` (`SettingsGroupItem`): rows separated by `divider` hairlines, a muted heading above each group and a muted footnote below it. A warning goes in a `warningSoft` callout, not orange text. A selected option shows a `fg` check, and switches use `Toggle` (`accent` track when on).
- Translucent roles (`hover`, `selected`, `divider`, `border*`, `dangerSoft`) are never a `backgroundColor`; `test/style-guard.test.ts` enforces this. Translucent edges stay allowed.

## Components

- Profile navigation opens a lightweight shell immediately. Heavy sections wait for the native opening transition; loading is visible independently of data arrival. A bounded Host-client/Bot cache supplies the last successful sections while refreshing in the background, and failed refreshes retain earlier data with retry. Model and permission editors keep their existing fresh-load/save paths. See [ADR-0219](../../docs/adr/0219-mobile-presentation-keeps-caches-and-stream-buffers-local.md).
- A drawer owns one `SheetStack`: its handle stays fixed while secondary pages push/back inside the same native sheet. Global usage, App icon and notifications, profile model/workspace/notifications, routine detail/create/edit, Token detail and memory files share this navigation. Child headers consume no second status-bar inset; headers and bodies use `theme.overlay.fill`, with raised content groups. Editors reuse their existing validation and Host mutation ports.
- Profile token totals retain reported usage when other calls are unknown, using the global Settings count format (`674.7K+`, for example). Completely unreported usage remains unknown; an idle, fully reported window may show zero.
- `src/ui/design/` holds the tokens and theme (ADR-0201).
- `src/ui/primitives/` holds `Text` (variant `meta` / `body` / `title`, and a tone that is a colour role), `Button`, `Toggle`, `SettingsRow`, `SettingsSection` and `SettingsGroupItem`, `CountBadge`, `Segmented` (the native segmented control: a SwiftUI segmented `Picker` on iOS, a Material 3 `SingleChoiceSegmentedButtonRow` on Android; each label is one short word so no segment wraps), `DayBars` (one bar per day or week, scaled to the busiest, optionally stacked in tones from `design/chart.ts`; an empty day keeps a stub on the layer's `inset`), `DayHeat` (a weeks × weekdays heatmap), and later `Icon`, `IconButton`, `Button`, `Avatar`, `Card`, `SettingsRow` and `EmptyState`.
- Forms use `TextField` from `primitives/text-field`: the `field` layer, a hairline `field` edge, `radius.md`, a touch-height minimum (two lines when multiline) and the system clear button on single-line fields. Give every field a placeholder or a visible label, and the keyboard and content type its value needs (`url`, `emailAddress`). `SearchField` leads with a magnifying glass and relies on the native iOS clear button; Android, which has none, adds its own.
- Follow the HIG for alerts and action sheets. An action that can't be undone (unpair, remove access, revoke, sign out, reset) asks first through `confirmDestructive`: a title that names the action, Cancel first, then the destructive button. A short list of actions on one item uses `showActionMenu`, which on iOS is an action sheet with the destructive action last and Cancel set apart; never show such a list as a centered alert.
- `src/ui/chat/` will hold the conversation row, bubble, message group, time separator, action cards, composer, working status and scroll-to-bottom.
- `src/ui/shell/` holds the Host drawer, Settings gear, display preferences, Channel section headers and the activity item.
- `app/` routes, reads the Host client, and composes these components.

## Code rules

1. **No literal style values.** Fills come from `theme.layer` (above).
   - Colours, font sizes and weights, spacing, radii and edge widths come from `useDesignTheme()` and `src/ui/design/tokens.ts`.
   - `test/style-guard.test.ts` enforces this for `app/` and `src/ui/`.
   - Files written before the rule are listed in it and leave the list once migrated; the test fails if a migrated file stays listed.
2. **Text goes through `primitives/text`.** Icons will go through `Icon` (`expo-symbols`).
   - All user-facing text and visible inputs follow the live system text size, without a global maximum or shrink-to-fit. Use `primitives/system-text` for inputs and legacy styled text. Decorative avatar initials may remain unscaled because the containing control exposes the full accessible label; remote Browser/Computer hidden keyboard capture fields remain native.
   - iOS uses native `dynamicTypeRamp`/UIFontMetrics: body, headline, footnote and title1 for body/title/meta/display. Legacy explicit sizes map to the matching semantic ramp. Android retains native nonlinear scaling; never multiply text metrics by a global font scale. RN 0.86 can reuse stale paragraph measurements after a live size change, so only noneditable root Text nodes renew at a new iOS font scale. This may end text selection during that system change; TextInput nodes never remount. Native TextInput supports the body ramp through its native view attributes even though its TypeScript interface omits the prop. Keep this adapter covered by native resize and subsequent-update checks. Base tokens remain unscaled for icons/layout.
   - Let controls grow with padding/minimum sizes; wrap essential button/form labels. Use `theme.largeText` to stack crowded metadata and choices. Composer measures its native body line, bounds the field to one fifth of the viewport (at least one complete line), and preserves the input node, draft and selection. Long drafts scroll inside the field and can expand into a full-screen editor that shares the same draft, mention suggestions and send path. Filter headings scroll with choices; large-text Usage summaries keep their amount semantic role and move the chart to the existing detail screen. Native navigation chrome and Markdown keep their platform scaling owners.
   - Follow the [system text and large-text acceptance contract](#system-text-and-large-text-acceptance) for implementation and native QA; source tests do not qualify native geometry.
   - Markdown bodies are the exception: `MarkdownView` renders them as native text with `react-native-enriched-markdown`, styled from the same tokens in `src/ui/markdown-style.ts`.
3. **A new visual element is added to `primitives/`, `chat/` or `shell/` first.** The PR says why the existing ones do not fit.
4. **Interactive elements meet the touch target and carry an `accessibilityLabel`.** The touch target is `theme.touch`: 44pt on iOS, 48dp on Android.
5. **Lists virtualize.** The chat is a top-to-bottom `FlatList` that starts at its end.
6. **Motion and haptics are limited.**
   - Motion uses Reanimated, only for bubble entry, a held bubble's lift, the message menu, card collapse, the status dot, the working row glyph, the Host drawer, the image viewer's gestures and the composer growing line by line (up to five lines, then it scrolls).
   - Haptics fire only on send, approve or deny, submitting a choice, and opening a message's menu.
7. **Copy lives in `src/ui/strings.ts`** and follows [UI copy](../../docs/agents/ui-copy.md): say Bot, keep hints and captions short and plain. Internal ids and protocol names stay out of the UI.
8. **UI PRs show the change.** Follow the [visual evidence rules](../../docs/agents/pr-ui-visual-evidence.md). Font, keyboard, native chrome and native control behavior require native captures and interaction checks; web previews are supplementary. Record source checks, platform-native results and Human QA separately.

## System text and large-text acceptance

This contract applies to new and changed Expo/React Native screens, shared components and text/input adapters. It is a review requirement, not a claim that every existing screen or platform has already passed. The implementation details above remain version-specific; recheck them when React Native or Expo changes.

### Preserve platform ownership

- Use semantic text roles through our shared primitives. iOS follows native Dynamic Type; Android follows native text scaling, including nonlinear scaling on supported versions. Do not impose one JavaScript multiplier on every text style, scale the entire UI, or apply native and manual scaling twice.
- Do not disable scaling, shrink text to fit, change a title to a smaller semantic role at a breakpoint, or set a global `maxFontSizeMultiplier` to conceal a layout defect. A narrow exception must name the element, explain its purpose and accessible alternative, and carry native evidence in the PR. Existing decorative initials and hidden capture fields do not justify exceptions for visible content.
- Keep native navigation and Markdown as their own scaling owners. Reuse the documented shared adapter for framework bugs; avoid screen-specific font workarounds. Live setting changes must retain editable fields, drafts, focus and mention metadata. Record any selection limitation rather than claiming complete editing acceptance.

Platform references: [Apple Dynamic Type and adaptive layouts](https://developer.apple.com/videos/play/wwdc2024/10074/) and [Android nonlinear font scaling](https://developer.android.com/about/versions/14/features#non-linear-font-scaling). Follow documentation for the installed SDK/RN versions when choosing concrete APIs.

### Reflow the task, not only the text

- Let rows and controls grow using padding and minimum sizes. Wrap essential titles, action labels, validation and request details. Secondary previews may truncate only when complete content remains reachable; never hide the information needed to make an approval or form decision.
- Stack crowded metadata and actions; give the conversation, message or decision priority over decorative labels, timestamps and charts. Keep a stable semantic role when moving content. Move secondary detail behind an accessible entry rather than squeezing the primary content.
- Make sheets and forms scroll to their last option, error and action. Large headings must not consume a fixed part of the viewport. Preserve list virtualization; do not wrap a virtualized list in another scroll container to solve text overflow.
- Measure floating surfaces and reserve matching content insets. Test status bars, safe areas and keyboard-open states. Primary actions must stay reachable and text must not be hidden beneath chrome. Maintain at least the existing 44pt iOS / 48dp Android touch targets and meaningful accessible names.
- Bound inline editing so a long draft does not consume the task view. Provide scrolling and, where needed, expanded editing that shares the same draft, selection/mention handling and send path. Test returning, cancelling/dismissing and sending; do not create a second draft authority.

### Native acceptance matrix

For affected screens, check **default, an intermediate enlarged size and the maximum system size, in both light and dark appearance, on iOS and Android**. Use the OS setting, not page zoom or a mocked `fontScale`. Record the actual category/percentage, OS, viewport and installed binary; the platforms' sizes are not numerically equivalent.

| Platform | Default                     | Intermediate enlarged                            | Maximum                                                    |
| -------- | --------------------------- | ------------------------------------------------ | ---------------------------------------------------------- |
| iOS      | `large`                     | `accessibility-large`                            | `accessibility-extra-extra-extra-large`                    |
| Android  | Default system font setting | An available setting between default and maximum | Device maximum; include 200% on Android 14+ when supported |

These iOS names identify the Simulator categories, not labels such as “Medium” in Settings. Also exercise live default → maximum → default changes while the view is open, with a subsequent ordinary update to catch stale measurements. Shared text/input adapter changes additionally cover the smallest setting and a return to default.

| Affected surface                      | Required interaction checks                                                                                                                                                                                 |
| ------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Lists / Activity / search             | Read primary content; expand/collapse, search, clear and dismiss; retain the query; reach pagination and the last row.                                                                                      |
| Sheets / settings / forms             | Reach the final option, reset, validation and primary action; apply/cancel/dismiss according to the existing contract.                                                                                      |
| Chat / composer / editor              | Keep a multiline draft through live resizing; edit with keyboard open, use mentions, return from expanded editing and send through the real Host path. Verify resulting content/metadata, not only the tap. |
| Approvals / questions / private input | Read the decision context and all choices, reach the actual response controls and verify the owning Host's outcome. A fixture without pending requests cannot pass this row.                                |

For shared primitives, cover representative screens from each row and record gaps explicitly. Check relevant long/localized labels and actual CJK IME composition when editing changes; include VoiceOver/TalkBack and orientation checks when navigation, labels, reading order or responsive layout changes. The three-size matrix is the minimum for the affected flow, not whole-app accessibility certification.

### Evidence and handoff

- Use the [shared device QA queue](../../docs/agents/device-qa.md) before starting a Simulator, Metro, Host or build. Preserve others' pairings and requests, then restore default font size/appearance and stop task-owned resources when finished.
- Capture matched native before/after states for the three sizes and both appearances on each tested platform. Match viewport, locale, test data and keyboard state; disclose scroll/caret differences. For a new view, label its former entry point or absence as Before. Embed sanitized, commit-pinned images in the PR body and verify they render.
- Report each platform/case as passed, failed, blocked or unrun, with source/batch/binary identities, actions and observed outcomes. Missing Android tooling or a device is a blocker, not a pass inferred from iOS. Record a runnable next check for every capture blocker.
- Source tests protect role mapping, nested text, input identity and behavior; they cannot establish native glyphs, keyboard geometry or usability. Screenshots alone cannot establish interaction, persistence, IME or screen-reader behavior. Keep source tests, native checks and Human acceptance distinct; documentation or green CI does not authorize merge.

## Responsive interactions

Navigation, drawer/sheet opening, tab selection and editable search respond before waiting for data. Commit the destination's title, selected control and usable back/dismiss controls immediately. Defer expensive first content until the shell has had a frame to present, using `DeferredContent` for retained page content; never add an arbitrary animation-duration timeout or await a network call before opening.

- Prefer the last successful content for the same Host and query while refreshing. An uncached result shows a bounded, noninteractive skeleton in its final layout; distinguish loading, empty, failure and content. A failed refresh keeps the content with a retry notice. Query identity includes every filter; changing Host must never reuse another Host's content. Bound inactive caches and release subscriptions when their page loses focus. Shared Host transport continues receiving.
- Prefetch a likely destination during idle time or intent when it helps the measured first visit. Deduplicate with the same cache the destination reads, cancel obsolete ownership and keep prefetch off the critical press path. Prefetch is an optimization, not a prerequisite for navigation.
- Separate focus/status-bar/chrome updates from expensive content. Preserve list, pager and editable-field identity across focus changes so scroll positions, choices and drafts survive. Memoization must address a measured invalidation and keep meaningful inputs stable; do not suppress updates with incomplete comparators.
- Virtualize long chat, roster and Activity lists. Streaming publishes update the active draft/tail; historical messages keep stable keys and avoid re-rendering for a pure tail append. Reading history owns its cursor until the user deliberately returns to the bottom. Exercise both history scrolling and scrolling during streaming.
- Measure tap-to-first-feedback and data-ready time separately, for cold, prefetched, warm/cached, slow and failed requests. Record the build, input size, query, device and instrumentation. Target 120 FPS means an 8.33 ms frame budget: report native presented-frame intervals/hitches and JS work separately, with the existing ABBA/three-run method. Development profiles identify work; production JavaScript on a Debug binary and a native Release build are different results. A 120 Hz setting, a skeleton screenshot or a smooth recording cannot qualify 120 FPS.

The shared Expo/React rules are platform-independent; native iOS and Android acceptance remain separate. Reference: [Expo prefetch behavior](https://docs.expo.dev/router/basics/navigation/#prefetching) and [React deferred rendering](https://react.dev/reference/react/useDeferredValue). Use APIs from the installed SDK source when current documentation differs.

## Keyboard and text entry

Structured mention links follow the Human-confirmed inline presentation in #2160: the avatar and `@name` share the body text's line box, with the Bot primary color adapted against the actual bubble surface using the same name-color function as Web. They wrap as inline text; do not impose a 44/48-point block height. This is an explicit exception to the general control-size rule for these inline links, not a new default for buttons. Keep accessible link labels and ID-bound actions.

Every editable field on iOS and Android belongs to a layout that responds to the keyboard. Keep the focused caret and the current editing line visible throughout keyboard opening, closing, interactive dismissal, focus changes and multiline growth. The user must be able to reach validation, submit, cancel and retry while editing, including at maximum system text size and in a partially expanded sheet.

- Forms use `KeyboardFormScroll` from `src/ui/primitives/keyboard-form.tsx`. It follows native keyboard frames and automatically reveals the focused field, reserving room for a following action. Put actions in the same scroll owner or a keyboard-tracking footer. Keep the draft and editable-field identity when layout changes.
- Virtualized forms use its stable `renderKeyboardFormScroll` adapter on the existing list. A virtualized list remains the sole scroll owner. Fixed search headers and full-screen editors use `KeyboardAvoidingView` from `react-native-keyboard-controller`; each screen has one owner for keyboard displacement. Chat retains its dedicated `KeyboardChatFrame` and composer tracking.
- Root `KeyboardRoot` supplies the keyboard controller on both native platforms. Modal windows and native form sheets need their own bounded layout; test their actual presented geometry. System resize alone and a keyboard-dismiss button do not establish visibility. Use native keyboard tracking instead of a timer or post-show measurement to reposition forms.
- Embedded WebView input keeps native viewport/scroll handling as its keyboard owner; verify the focused web field and web action too. Modern Android WebView resizes its visual viewport for IME overlap ([platform contract](https://developer.android.com/develop/ui/views/layout/webapps/understand-window-insets)). Verify older WebView providers explicitly and check for duplicate insets before adding a native resize wrapper. Remote Browser/Computer text entry must keep the remote caret visible in the resized stage.
- Verify each changed input path with the real soft keyboard: open it from a low field, type and move the caret through several lines, switch focus while it stays open, reveal and activate the form action, dismiss/reopen, and verify draft preservation after a failed save. Repeat default/intermediate/maximum system text in light/dark on each available platform. Record unavailable native cases explicitly; source tests and hidden or floating keyboards cannot prove soft-keyboard clearance.

### Shared drawer title treatment

The workspace drawer starts with its category tabs. `DrawerHeader` supplies generic bottom `Sheet` headers in the iOS 26 sheet layout: an optional leading close (×), a centred semantic title with an optional decorative icon, and an optional trailing confirm (✓) for sheets that commit a change. Empty slots keep their width so the title stays centred, and close and confirm are each independently accessible. The title is plain bold text on the sheet's opaque overlay, with no capsule, on both platforms; close, back and confirm are quiet filled circles on the overlay's `raised` fill, matching the native iOS 26 back button of a sheet's child page. A sheet is already a clean overlay above the screen, so it gets no glass: Liquid Glass is only for controls that float over content that must stay visible beneath them, such as the chat header over messages or the navigation island over a list. Child pages of a sheet stack (`SheetStack`) use the native iOS navigation bar with its minimal back button and centred title; Android draws the same row with `DrawerHeader` and `onBack`, so a child page's back sits where the root page's close sits. The close target is at least the platform touch minimum. Long titles wrap without changing the font scale; subtitles remain outside the capsule.

Material is a decorative background only: text, focus, hit testing and navigation remain in the existing React Native tree. A color-scheme change recreates native glass backdrops and the bottom navigation button presentations so they cannot retain the previous appearance. The owning React page, selected route, source scope and menu state remain mounted; native accessibility focus after an appearance change requires separate device verification. It must not capture gestures or become another accessibility element. Drawer body and grabber stay opaque and continuous. Header styling does not add dismissal controls to Settings or other native `SheetStack` routes; those retain their established handle/back policy until separately verified.

For same-name Organization tabs, show a collision-only secondary source label (Organization identifier suffix plus service host), with full source/Organization identity in the accessible name. Expand the suffix when needed to distinguish same-service identifiers. Routing and ordering continue to use stable source keys. Unique names stay compact.
